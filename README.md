## 30초 안에 이해하기

AIARC는 **준공 단계에서 반복되는 문서 취합·정리·누락 확인·보완 업무를 줄이는 Windows 데스크톱 AI 앱**에서 시작합니다.

하지만 AIARC가 만들려는 최종 제품은 준공 문서 정리도구가 아닙니다.

> **프로젝트의 문서·도면·메일·사진과 변경 흔적을 한 프로젝트 맥락으로 연결하고, AI가 지금 무엇이 유효하고 무엇이 바뀌었으며 무엇을 해야 하는지 이해하는 건축·건설 AI Project Workspace를 지향합니다.**

그 중심에 **Project State**가 있습니다. Project State는 파일 목록이 아니라 프로젝트의 현재 상태와 변화의 이유를 이어서 이해하는 프로젝트의 기억입니다.

```text
현재
준공 문서 자동화

↓

다음 제품
AI Project Workspace

↓

핵심 능력
Project State
무엇이 유효하고, 무엇이 바뀌었고, 무엇이 미결인지 이해

↓

장기
Architecture AI
```

그렇다면 왜 준공 문서부터 시작할까요?

준공 단계에는 설계·시공·감리·자재·품질 등 프로젝트 전 과정에서 만들어진 결과물이 모입니다. AIARC는 이 지점에서 먼저 **AI가 실제 프로젝트 자료를 읽고, 문서의 종류와 관계·최신본·누락·변경 반영 여부를 이해할 수 있는지** 검증합니다.

현재 0.6.0 프로토타입은 단순한 임시 문서정리 화면이 아니라, 장기적으로 Project State를 만들기 위해 필요한 첫 번째 능력인 **문서 이해와 관계 연결**을 검증하는 시작점입니다.

```text
현장 폴더 / ZIP
→ AIARC 분석
→ 문서 분류 · 관계 연결
→ 누락 · 중복 · 최신본 후보 · 확인 필요
→ 전체 정리
→ 예외와 원문 근거 확인
```

이 아이디어는 건축사사무소에서 건축사보로 근무하며 감리·사용승인 실무에 참여하는 과정에서 출발했습니다. 준공 단계에서는 건설사로부터 전달된 자료를 확인하고, 빠진 자료를 요청하고, 수정·보완본과 최신본을 반영해 제출 가능한 상태로 맞추는 일이 반복됩니다.

준공 단계에서 프로젝트 자료의 관계와 상태를 이해하는 능력을 먼저 검증하고, 같은 능력을 공사 중으로 앞당겨 프로젝트의 변화와 미결사항을 계속 이해하는 AI 업무공간으로 확장합니다.

> **공사가 끝나도, 서류는 끝나지 않습니다.**  
> **AIARC로 공사와 서류를 한 번에 준공하세요.**

## 왜 이 문제인가

### 1. 실제 실무에서 반복됩니다

준공 단계에서는 자료를 한 번 받았다고 일이 끝나지 않습니다.

```text
자료 확인
→ 누락 확인
→ 보완 요청
→ 수정·보완본 수신
→ 최신본 반영
→ 최종 제출용 서류 세트 완성
```

AIARC가 없애려는 것은 전문가의 검토나 책임이 아닙니다. **검토 사이에 반복되는 찾기·정리·대조·누락 확인·보완 요청·수정본 반영·추적**을 줄이는 것이 목표입니다.

### 2. 법과 제도에서도 확인되는 업무입니다

현행 「건축법」과 하위법령에는 감리, 건축자재 품질관리, 사용승인 과정에서 문서와 도서를 작성·기록·확인·전달·첨부·제출하는 절차가 존재합니다.

모든 문서가 같은 순서로 이동하는 것은 아닙니다. 다만 일부 품질관리 문서처럼 여러 참여자의 확인과 전달이 법령에 구체적으로 연결된 사례가 있고, 감리·사용승인에도 문서 작성과 확인, 제출 절차가 존재합니다.

즉 이 문제는 단순한 파일정리 습관이 아니라 **실제 감리·검토·사용승인 절차와 연결된 업무**입니다.

### 3. 이미 사람의 시간과 비용이 들어갑니다

착공·준공서류, 감리 관련 서류, 설계변경 등 건설 공무 문서업무는 외주·대행 서비스의 대상이기도 합니다.

이 사실은 **일부 문서업무는 사람이 직접 시간을 쓰거나 외부 비용을 지불해서 해결하고 있다는 점**을 보여줍니다.

## 초기 고객과 진입 전략

AIARC의 초기 고객은 건축·건설 프로젝트에서 문서를 직접 취합하고, 누락을 확인하고, 보완본과 최신본을 반영하는 실무자입니다. 창업자 역시 건축사사무소에서 감리·사용승인 업무에 참여하며 같은 작업을 직접 수행하고 있습니다.

초기 제품은 회사 전체의 업무방식을 바꾸거나 여러 참여자가 동시에 새로운 시스템에 들어와야만 가치가 생기는 구조로 시작하지 않습니다. 기존처럼 폴더, ZIP, 이메일로 자료를 전달받아도 AIARC 사용자 한 명이 자신의 PC에서 바로 문서 정리와 검토 업무를 줄일 수 있도록 설계합니다.

이 업무에는 이미 사람의 시간과 일부 외주 비용이 투입되고 있습니다. AIARC는 기존 업무환경 위에 바로 얹어 사용할 수 있는 Windows 도구로 시작해, 개인 실무자와 소규모 조직에서 자연스럽게 도입되는 것을 첫 진입점으로 삼습니다.

## 현재 제품: 준공 문서 자동화

AIARC는 큰 비전을 한 번에 구현하지 않습니다.

첫 제품은 **준공 단계의 문서 수집·정리·누락 검토**입니다. 프로젝트 전 과정의 결과물이 모이는 준공 단계에서 AI가 문서의 종류와 관계, 누락, 최신본 후보를 얼마나 잘 파악할 수 있는지 먼저 검증합니다.

```text
현장 폴더 / ZIP
        ↓
      AIARC
        ↓
문서 인식 · 분류 · 관계 연결
        ↓
누락 / 확인 필요 / 중복 / 최신본 후보
        ↓
       [전체 정리]
        ↓
정리된 문서 트리 + 검토할 예외만 표시
```

현재 제품의 목표는 단순합니다.

> **사람이 모든 파일을 처음부터 다시 열어보지 않아도, 정리된 결과와 확인할 예외부터 볼 수 있게 하는 것입니다.**

동시에 이 단계는 Project State에 필요한 첫 번째 질문을 검증합니다.

> **AI가 실제 건축 프로젝트의 문서를 읽고, 서로 어떤 관계이며 무엇이 현재 유효한 자료인지 이해할 수 있는가?**

## 다음 제품: AI Project Workspace

준공 문서 자동화에서 검증한 능력을 프로젝트 전체로 확장하면 다음 질문이 생깁니다.

> **프로젝트 자료가 계속 들어오는 동안 AI가 지금 무엇이 유효하고, 무엇이 바뀌었고, 무엇을 해야 하는지 계속 이해할 수 있는가?**

AIARC가 다음 제품 단계에서 지향하는 **AI Project Workspace**는 프로젝트의 문서·도면·메일·사진을 한 프로젝트에 연결하고, AI가 현재 상태와 변경 이력을 이해해 질문과 다음 업무까지 이어주는 건축·건설 AI 업무공간입니다.

```text
프로젝트 자료 유입
문서 · 도면 · 메일 · 사진 · 변경 기록
                ↓
문서 자동 정리와 관계 파악
                ↓
Project State
현재 상태 · 변경 · 미결사항 · 근거
                ↓
Project AI
검색 · 질문 · 설명
                ↓
필요한 다음 업무로 연결
```

새로운 시스템으로 모든 사람을 먼저 이주시키는 것이 출발점은 아닙니다. 기존 폴더·ZIP·이메일 중심 업무를 존중하면서, 들어오는 자료를 같은 프로젝트 맥락으로 연결하는 방향을 지향합니다.

### 기존 저장·협업 도구와 무엇이 다른가

일반적인 저장·협업 도구의 중심은 **파일을 모으고 공유하고 찾는 것**입니다.

AIARC가 차별화하려는 지점은 그 다음입니다.

```text
기존 저장·협업 도구
파일을 모으고 전달하고 찾는다

                ↓

AIARC
파일과 업무 흔적 사이의 관계를 이해하고
무엇이 바뀌었는지 추적하며
현재 무엇이 유효하고 무엇이 미결인지 파악한다
```

즉 Workspace는 단순한 새로운 저장공간이 아니라 **Project State를 계속 만들고 사용할 수 있게 하는 업무공간**입니다.

## 왜 Project State가 필요한가

건축 프로젝트의 실제 상태는 폴더 하나에 완성된 형태로 존재하지 않습니다.

예를 들어 한 공사에서 다음과 같은 변화가 있었다고 가정합니다.

```text
7월 3일   원도면 A
    ↓
7월 12일  현장 변경지시
    ↓
7월 13일  수정도면 B
    ↓
7월 14일  회의록 / 메일 기록
    ↓
7월 15일  변경된 내용으로 실제 시공 / 현장사진
    ↓
7월 18일  관련 자재 추가 발주
```

몇 달 뒤 누군가 묻습니다.

> **“이 부분 원래 이렇게 되어 있었어?”**  
> **“언제, 왜 바뀐 거야?”**

일반적인 파일 중심 환경에서는 도면, 회의록, 메일, 사진, 발주서가 서로 다른 위치에 흩어져 있고 사람이 다시 찾아 기억을 복원해야 합니다.

AIARC가 지향하는 Project State는 그 변화를 다음처럼 이해합니다.

```text
원래 상태        A
      ↓
변경지시
      ↓
수정도면          B
      ↓
회의 / 메일 확인
      ↓
실제 시공

현재 상태        B
변경 근거        관련 도면 · 회의록 · 메일 · 사진
남은 미결사항    관련 후속업무
```

그래서 사용자는 파일명을 기억하지 않아도 다음처럼 물을 수 있습니다.

> **“왜 A에서 B로 바뀌었어?”**  
> **“관련 근거를 전부 보여줘.”**

AIARC가 지향하는 답은 단순한 검색결과가 아니라 **현재 상태 + 변화의 흐름 + 원문 근거**입니다.

> **Project State는 프로젝트의 기억입니다. 그 기억이 있어야 AI가 지금 무엇이 맞는지뿐 아니라, 왜 그렇게 되었는지 설명할 수 있습니다.**

## 차별점: 준공 때 모으는 대신, 공사 중 함께 완성합니다

현재 프로토타입은 **준공 시점에 이미 흩어진 자료를 정리하는 경험**을 먼저 보여줍니다.

다음 제품 단계에서는 같은 자동화 능력을 공사 중으로 앞당깁니다.

```text
프로젝트 생성
→ 프로젝트 코드 / 초대 링크
        ↓
프로젝트에 필요한 역할의 참여자가 자료 추가
        ↓
AIARC 자동 분류 · 관계 연결 · 버전 관리
        ↓
누락 · 보완 · 최신 유효본 · 확인 필요 상태 갱신
        ↓
수정본 · 보완 결과 · 확인 결과 누적
        ↓
공사 완료
        ↓
누적된 유효 자료에서 준공 · 사용승인용 최종 서류 세트 생성
```

전문가가 확인해야 할 내용은 전문가가 확인합니다. AIARC는 그 전후에서 반복되는 **정리·누락 확인·보완 요청·수정본 반영·전달·추적**을 맡습니다.

### 이 구조의 차별점

**1. 자료가 생길 때부터 프로젝트에 연결됩니다.**  
준공 직전에 여러 회사의 폴더와 메일을 처음부터 다시 합치는 양을 줄입니다.

**2. AI가 문서의 생애주기와 프로젝트의 변화를 이어서 봅니다.**  
단순 저장이 아니라 문서 관계, 최신 유효본, 누락, 보완, 변경과 확인 상태를 계속 추적합니다.

**3. 공사가 끝날 때 서류도 거의 끝난 상태를 목표로 합니다.**  
공사 중 생성·확인·보완된 자료가 계속 누적되기 때문에, 공사가 끝난 뒤 처음부터 다시 정리하는 일을 줄입니다.

프로젝트 코드나 공동 저장공간 자체가 차별점은 아닙니다. 핵심은 **자료가 쌓이는 동안 AI가 프로젝트 상태를 계속 이해하고, 그 상태를 실제 다음 업무와 준공 결과물까지 이어주는 것**입니다.

> **건물을 짓는 동안, 준공서류도 함께 완성됩니다.**

---

## AI가 무엇을 이해해야 하는가

건축 프로젝트의 현재 상태는 파일 하나나 폴더 하나만 봐서는 알기 어렵습니다.

같은 문서와 도면도 프로젝트가 진행되면서 검토되고, 승인되고, 변경되고, 새 버전으로 대체됩니다. 요청과 보완, 수정본과 회신은 이메일과 첨부파일을 통해 오가기도 합니다.

AIARC는 이런 흔적을 연결해 다음을 이해하는 방향으로 발전합니다.

- 이 자료가 어느 현장·공종·업무와 연결되는가
- 현재 유효한 문서와 도면은 무엇인가
- 무엇이 누락됐는가
- 어떤 보완이 진행 중인가
- 무엇이 언제 어떻게 바뀌었는가
- 어떤 근거로 현재 상태가 되었는가
- 지금 확인하거나 처리해야 할 일은 무엇인가

내부적으로 이 방향을 **Project State Reconstruction → Next-action Execution**이라고 부릅니다.

```text
문서 · 도면 · 메일 · 사진 · 변경 기록
                    ↓
        프로젝트 현재 상태와 변화 파악
                    ↓
          미결사항 · 다음 업무 판단
                    ↓
                  실행
                    ↓
             상태 다시 갱신
```

공개 제품 설명에서 중요한 것은 영어 용어가 아니라 결과입니다.

> **흩어진 자료를 다시 찾고 맞추는 일을 줄이고, 지금 무엇이 유효하며 왜 그렇게 되었고 다음에 무엇을 해야 하는지 바로 알 수 있게 한다.**

## 제품 경험

AIARC는 범용 챗봇이 아니라 **자동화가 먼저 일하는 Windows 데스크톱 작업공간**을 지향합니다.

```text
파일 / 폴더 / ZIP 투입
↓
AIARC 자동 분석
↓
문제가 없는 문서는 자동 처리
↓
누락 · 충돌 · 애매한 판단만 표시
↓
사용자는 필요한 순간에만 확인
```

핵심 원칙:

- 기존 Windows 폴더·이메일·HWP 중심 업무환경을 존중합니다.
- 문제가 없는 문서는 자동 처리하고 예외만 보여줍니다.
- AI 판단은 가능한 한 원문 근거와 연결합니다.
- 법적·기술적 최종 판단과 실제 날인·서명은 사람이 합니다.
- 원본 파일은 안전하게 보존하고 자동화 결과는 되돌릴 수 있어야 합니다.

## 현재 단계

**Stage: Prototype / validation**

현재 AIARC 0.6.0은 준공 문서 자동화의 제품 경험을 보여주는 프로토타입이면서, **Project State에 필요한 첫 번째 capability인 프로젝트 문서 이해·분류·관계 연결을 검증하는 단계**입니다.

현 단계에서는 실제 제품으로 이어질 UI/UX와 핵심 업무 흐름을 먼저 시연합니다. 이후 실제 현장자료를 이용해 문서 분류, 관계 연결, 최신본 후보, 누락·불일치 탐지, 업무시간 절감 효과를 검증합니다.

AI Project Workspace와 Project State 전체가 현재 0.6.0에 구현됐다는 뜻은 아닙니다. 현재 제품이 검증한 능력을 다음 단계에서 프로젝트 전체의 자료와 변화로 확장합니다.

프로토타입에서 시뮬레이션되는 기능도 실제 구현 범위와 구분해 공개합니다.

## 어디까지 가는가

```text
준공 문서 자동화
→ AI Project Workspace
→ Project State
→ Project Intelligence
→ Architecture / Construction Agent
→ Architecture AI
```

준공 문서 자동화는 최종 목적이 아니라 **AI가 실제 건축 프로젝트의 자료·관계·변화를 이해할 수 있는지 검증하는 첫 제품**입니다.

장기적으로 AIARC는 문서뿐 아니라 법규, 설계, 도면, BIM, 견적, 공정, 자재, 품질, 인허가 등 **건축 프로젝트의 더 넓은 지식업무까지 다루는 Architecture AI**를 목표로 합니다.

다만 각 단계의 가치는 실제 사용자와 실제 프로젝트 자료에서 검증해야 합니다.

> **Architecture AI가 프로젝트를 수행하려면 먼저 프로젝트가 지금 어떤 상태인지 이해해야 합니다. AIARC는 그 상태를 실제 업무에서 먼저 만들고 검증합니다.**
