# AIARC Public Roadmap

## 현재 출발점

AIARC는 **준공 문서 자동화**에서 시작합니다.

현재 0.6.0 프로토타입은 준공 단계에 이미 흩어져 있는 자료를 분석하고, 분류·누락·중복·최신본 후보와 확인할 예외를 보여주는 제품 경험을 시연합니다.

```text
현장 폴더 / ZIP
→ 분석
→ 문서 분류 · 관계 연결
→ 누락 / 중복 / 최신본 후보 / 확인 필요
→ 전체 정리
→ 근거 확인
```

현재 단계의 핵심 질문은 단순합니다.

> **사람이 모든 파일을 처음부터 다시 확인하는 양을 실제로 줄일 수 있는가?**

---

## 초기 진입 원칙

AIARC의 초기 고객은 건축·건설 프로젝트에서 문서를 직접 취합하고, 누락을 확인하고, 보완본과 최신본을 반영하는 실무자입니다.

첫 제품은 회사 전체의 시스템 교체나 여러 외부 참여자의 동시 도입을 전제로 하지 않습니다. 다른 참여자는 기존처럼 폴더, ZIP, 이메일로 자료를 보내도 되고, AIARC 사용자 한 명이 자신의 PC에서 바로 문서 정리와 검토 업무를 줄일 수 있어야 합니다.

즉 초기 진입점은 **기존 업무환경 위에 바로 얹어 쓰는 Windows 도구**입니다.

---

## Phase 1 - 실제 준공 문서 제품

프로토타입을 실제 현장에서 반복 사용할 수 있는 제품으로 발전시킵니다.

주요 범위:

- Windows 현장 폴더
- HWP / HWPX
- PDF / Excel / 이미지 / 도면
- 이메일 첨부파일
- 문서 자동 분류
- 문서 관계 연결
- 중복·최신본 후보
- 누락 탐지
- 제출 준비
- AI 판단 근거 확인

첫 번째 실제 제품은 준공 문서 업무입니다.

### 공사 중으로 확장

AIARC의 확장 방향은 **준공 시점에 하던 정리를 자료가 만들어지는 시점으로 앞당기는 것**입니다.

```text
프로젝트 코드 / 초대 링크
        ↓
자재 제조·유통업체 · 시공자 · 설계 · 감리 · CM 등
프로젝트에 필요한 역할의 참여자가 자료 추가
        ↓
AIARC 자동 분류 · 관계 연결 · 버전 관리
        ↓
누락 · 보완 · 최신 유효본 · 확인 필요 상태 갱신
        ↓
각 참여자는 자기 업무에서 확인할 항목 중심으로 검토
        ↓
수정본 · 보완 결과 · 확인 결과 누적
        ↓
공사 완료
        ↓
누적된 유효 자료에서 준공 · 사용승인용 최종 세트 생성
```

여기서 `설계`, `감리`, `CM`, `시공`은 서로 다른 사람을 뜻하지 않습니다. 실제 프로젝트에서는 같은 사람이나 조직이 둘 이상의 역할을 맡을 수 있습니다.

프로젝트 코드 자체가 차별점은 아닙니다. 핵심은 **여러 역할의 참여자가 자료를 쌓는 동안 AI가 문서 상태를 계속 관리해 준공 직전의 재취합·재정리를 줄이는 구조**입니다.

다만 이 공동 workflow는 초기 제품이 가치를 만들기 위한 필수 조건이 아닙니다. AIARC는 먼저 사용자 한 명이 기존 폴더·ZIP·이메일 환경에서 바로 이득을 얻는 구조로 시작합니다.

> **건물을 짓는 동안, 준공서류도 함께 완성됩니다.**

## Phase 2 - Document Lifecycle AI

파일의 종류만 분류하지 않고 문서가 **왜 생겼고, 무엇과 연결되며, 현재 어떤 상태인지** 이해하는 단계입니다.

대상:

- 품질·자재 문서
- 자재승인
- 검측
- 설계변경
- 도면 revision
- 승인·보완·회신
- 준공·사용승인

AIARC는 생성 → 검토 → 승인 → 변경 → 최신본 → 최종 제출로 이어지는 문서의 생애주기를 연결합니다.

이 단계에서 쌓이는 관계와 상태 정보가 이후 더 넓은 프로젝트 이해의 기반이 됩니다.

---

## Phase 3 - Project State Reconstruction

문서뿐 아니라 프로젝트에서 생기는 여러 흔적을 연결해 **현재 무엇이 유효하고 무엇이 미결인지 파악하는 단계**입니다.

```text
문서
+ 도면
+ 메일
+ 사진
+ BIM
+ 일정
+ 계약·원가
+ 승인·변경 기록
```

AIARC가 파악해야 하는 것:

- 현재 유효한 도면과 문서
- 완료된 승인과 미결사항
- 반영된 변경과 아직 반영되지 않은 변경
- 프로젝트별 관계자와 업무 흐름
- 누락된 정보와 충돌하는 정보
- 현재 단계에서 다음에 처리해야 할 업무

내부적으로 이 구조를 **Project State Reconstruction**이라고 부릅니다.

---

## Phase 4 - Project Intelligence

현재 상태를 바탕으로 위험, 충돌, 지연, 누락과 미결사항을 지속적으로 파악하는 단계입니다.

예:

- 지금 이 프로젝트에서 무엇이 진행 중인가
- 어떤 결정이 아직 내려지지 않았는가
- 최신 도면과 실제 시공상태가 일치하는가
- 어떤 변경이 다른 문서·공정·비용에 영향을 주는가
- 사람이 가장 먼저 확인해야 할 것은 무엇인가

핵심 변화:

> **자료를 이해하는 AI → 프로젝트의 현재 상태를 지속적으로 이해하는 AI**

---

## Phase 5 - Architecture / Construction Agent

프로젝트 상태를 이해하는 데서 끝나지 않고, 반복 가능한 업무를 실제로 수행하는 방향으로 확장합니다.

장기 대상:

- 법규·대지 검토
- 설계 검토
- 도면 비교·수정
- BIM
- 견적·물량·공정
- 자재·품질·검측
- 설계변경
- 인허가 자료
- 메일·공문·회신
- 준공
- 유지관리 인계

```text
현재 프로젝트 상태
↓
다음 업무 판단
↓
필요한 도구 / 전문 Agent 실행
↓
결과와 근거 제시
↓
사람의 승인 또는 예외 확인
↓
프로젝트 상태 갱신
```

법적·기술적 최종 판단과 책임은 사람에게 남기고, 반복 가능한 업무부터 자동화합니다.

---

## Phase 6 - Architecture AI

장기 North Star는 **Architecture AI**입니다.

AIARC는 문서에서 시작해 프로젝트 정보를 더 넓게 이해하고, 필요한 전문 도구와 함께 건축 프로젝트의 지식업무를 수행하는 방향으로 확장합니다.

```text
준공 문서 자동화
→ Document Lifecycle AI
→ Project State Reconstruction
→ Project Intelligence
→ Architecture / Construction Agent
→ Architecture AI
```

---

## 왜 문서부터 시작하는가

준공 단계에는 프로젝트 전 과정에서 생성된 결과물이 모입니다.

그래서 다음을 한꺼번에 확인해야 합니다.

- 문서 종류
- 관계
- 누락
- 최신본
- 변경 반영 여부
- 제출 준비 상태

AIARC는 이 지점에서 먼저 **프로젝트 자료의 관계와 상태를 제대로 이해할 수 있는지** 확인합니다.

문서를 정리하는 것 자체가 최종 목적은 아닙니다. 실제 사용자가 반복해서 겪는 문제부터 해결하고, 그 능력을 더 넓은 프로젝트 업무로 확장합니다.

> **현재 문제를 제대로 해결한 뒤, 그 능력을 더 넓은 프로젝트 업무로 확장합니다.**

상세 구현계획, 평가체계와 내부 R&D 로드맵은 비공개 개발 저장소에서 관리합니다.
