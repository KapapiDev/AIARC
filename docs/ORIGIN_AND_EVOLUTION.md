# AIARC 문제 인식과 설계 발전과정

Updated: 2026-09-04

이 문서는 AIARC가 어떤 문제에서 출발했고, 왜 현재의 제품 구조에 도달했는지를 기록한다.

기능 목록보다 중요한 것은 **문제 발견의 과정과 제품 정의가 어떻게 좁혀지고 깊어졌는가**다.

---

## 1. 시작점: 공무업무는 필수지만 사람의 기억과 반복작업에 붙어 있다

건설 프로젝트에는 착공, 자재승인, 검측, 기성, 설계변경, 준공·사용승인 등 많은 공무업무가 발생한다.

규모가 큰 회사는 전담 인력이 수행할 수 있지만, 소규모 회사나 프로젝트가 불규칙한 조직은 상시 전문인력을 두기 어렵다. 시장에 착공·준공·자재승인·설계변경 서류 등을 대신 작성하는 공무대행 서비스가 존재하는 것도 이 업무가 단순한 불편을 넘어 실제 비용을 지불하고 해결하는 문제임을 보여준다.

하지만 여기서 첫 한계가 보였다.

> **공무업무 전체를 사람 대신 맡아주는 방식은 결국 또 하나의 인력집약적 대행회사가 될 수 있다.**

기성률, 설계변경, 현장상황 판단처럼 경험과 책임이 중요한 업무까지 전부 자동화하려 하면 제품 범위는 커지고 신뢰·책임 문제도 커진다.

그래서 질문을 바꿨다.

> **사람의 전문판단은 남기되, 매일 반복되는 문서 운영 자체를 얼마나 소프트웨어가 끝낼 수 있는가?**

---

## 2. 첫 번째 좁힘: 공무 전체가 아니라 문서 workflow

건설 공무를 실제 행동으로 나누면 반복되는 패턴이 있었다.

```text
자료를 받는다
→ 읽는다
→ 어느 현장/공종/자재인지 판단한다
→ 관련 자료와 연결한다
→ 폴더에 넣는다
→ 누락을 확인한다
→ 회사/법정서식을 작성한다
→ 관계자에게 보낸다
→ 회신을 받는다
→ 최신본을 교체한다
→ 최종 제출 때 다시 전체를 대조한다
```

이 과정에는 전문판단도 있지만 상당 부분은 **수집·분류·작성·전달·추적·정리**다.

AIARC의 첫 형태는 여기서 시작했다.

> **건설 서류를 자동으로 정리해주는 AI**

그러나 곧 `정리`만으로는 문제의 절반밖에 해결하지 못한다는 것이 보였다.

---

## 3. 실제 준공서류 구조가 문제의 크기를 보여줬다

실제 준공 세트는 PDF 몇 개를 한 폴더에 넣는 수준이 아니다.

현장에 따라 준공도면, 사진첩, 측량자료, 자재승인원, 품질시험성과, 각종 검사필증, 폐기물처리확인서, 에너지 관련서류, 건축자재 품질관리서, 시험성적서와 납품확인서 등 **수십 종류의 제출 항목**이 생긴다.

중요한 발견은 이것이었다.

> **준공 문제는 준공 직전에 시작되는 것이 아니다.**

공사기간 내내 이메일과 현장폴더에 자료가 쌓이고, 최신본과 관계자 회신 상태가 달라진다. 준공 직전에는 그동안 쌓인 문서를 사람이 다시 찾아 맞추고 빠진 자료를 요청한다.

그래서 제품 질문이 바뀌었다.

> **준공 때 한 번 정리하는 것이 아니라, 공사 중 자료가 들어오는 순간부터 계속 ‘준공 가능한 상태’를 유지하면 어떨까?**

이 지점에서 AIARC는 `준공서류 생성기`가 아니라 **지속적으로 문서 상태를 유지하는 앱**으로 발전했다.

---

## 4. 두 번째 전환: 새 SaaS가 아니라 기존 업무환경 위에서 작동해야 한다

건설회사에 새 웹서비스를 주고 모든 자료를 다시 올리라고 하면 업무를 줄이는 대신 또 하나의 입력업무를 만든다.

실제 자료는 이미 여기 있다.

```text
Outlook / Gmail
Windows 현장폴더
회사 공유폴더
다운로드 폴더
HWP / PDF / Excel / 이미지 / 도면
```

그래서 제품 원칙이 정해졌다.

> **사용자가 원래 하던 대로 메일을 쓰고 폴더에 저장하면 AIARC가 그 위에서 일한다.**

이것이 local-first 방향의 출발점이다.

local-first는 보안 문구만을 뜻하지 않는다.

- 기존 Windows 업무방식과 맞는다.
- 대용량 현장자료를 새 클라우드로 전부 이관하지 않아도 된다.
- 회사 내부 폴더구조를 유지할 수 있다.
- HWP와 한컴오피스 같은 국내 실무도구에 가까이 붙을 수 있다.

즉 AIARC는 사용자를 새로운 시스템 안으로 끌고 들어가는 대신, **기존 시스템 사이에 실행 레이어로 들어가는 제품**을 지향한다.

---

## 5. 세 번째 전환: 받은 문서뿐 아니라 작성하는 문서까지

건설 공무에는 외부에서 받는 자료만큼 직접 작성해야 하는 문서가 많다.

특히 국내 건축·건설 업무는 법정서식, 기관서식, 감리·회사양식에서 HWP 비중이 높다.

같은 현장명, 주소, 건축주, 시공사, 감리자, 공사기간, 자재정보 등을 여러 문서에 반복 입력한다.

그래서 제품 범위가 다음처럼 확장됐다.

```text
정리
+
문서 생성
```

다만 중요한 경계를 세웠다.

> **AI가 백지에서 법정문서를 임의로 작성하는 것이 아니라, 실제 사용하는 서식에 신뢰 가능한 현장데이터와 증빙에서 추출한 값을 넣는 방식이 우선이다.**

이 원칙은 지금도 유지한다.

---

## 6. 품질관리서가 ‘문서 lifecycle’ 문제를 선명하게 만들었다

「건축법 시행령」 제62조는 대상 건축자재의 품질관리서가 공급·시공·감리 단계를 거쳐 건축주와 허가권자 제출로 이어지는 구조를 규정한다.

```text
제조업자
→ 유통업자
→ 공사시공자
→ 공사감리자
→ 건축주
→ 사용승인 신청 시 허가권자
```

법령 참고: https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1025183813

현장에서는 서식과 증빙이 이메일로 오가며 관계자 확인·날인본과 수정본이 쌓일 수 있다.

사람은 그 과정에서 계속 기억해야 한다.

- 지금 어느 단계인가
- 누구에게 보냈는가
- 회신이 왔는가
- 받은 파일이 최신본인가
- 관련 증빙이 모두 있는가
- 다음 사람에게 보내야 하는가
- 최종본은 무엇인가

이 순간 제품 문제는 `파일관리`보다 정확하게 정의됐다.

> **문서가 상태를 갖고 이동하는 workflow 문제다.**

그래서 AIARC는 다음 구조로 바뀌었다.

```text
정리
+
생성
+
메일 실행
+
회신 추적
+
버전/상태 관리
+
최종 제출
```

## 7. 이메일은 부가기능이 아니라 workflow의 운송수단이다

AIARC에서 이메일은 단순한 `메일 보내기 기능`이 아니다.

```text
문서상태 판단
→ 다음 관계자 결정
→ 보낼 문서 선택
→ 요청메일 작성
→ 사용자 확인
→ 발송
→ reply/thread 감지
→ 첨부파일 인식
→ 기존 문서와 연결
→ 상태 갱신
→ 다음 행동
```

이 설계에는 중요한 장점이 있다.

**외부 관계자가 AIARC를 설치하지 않아도 된다.**

제조사, 자재업체, 감리단, 설계사 등은 기존 이메일을 그대로 쓰고, AIARC 사용자의 앱이 그 회신을 workflow 안으로 흡수할 수 있다.

---

## 8. 파일목록에서 Project Document Graph로

파일 중심 프로그램은 이렇게 본다.

```text
현장폴더
├─ 시험성적서.pdf
├─ 납품확인서_최종.pdf
└─ 품질관리서_rev4.hwp
```

AIARC가 지향하는 구조는 다르다.

```text
Project
└─ 외벽 단열재
   ├─ 제조업자
   ├─ 유통업자
   ├─ 제품/규격
   ├─ 시험성적서
   ├─ 납품확인서
   ├─ 품질관리서
   │  ├─ Rev.1
   │  ├─ 제조 확인본
   │  ├─ 유통 확인본
   │  ├─ 시공 확인본
   │  └─ 감리 회신 대기
   ├─ 관련 Email thread
   └─ 준공 제출상태
```

문서, 자재, 관계자, 메일, 버전, workflow를 연결하면 다음 질문에 답할 수 있다.

- 최신 승인본은 무엇인가
- 감리에게 보냈지만 답 없는 문서는 무엇인가
- 준공에 필요한데 없는 자료는 무엇인가
- 같은 자재의 증빙끼리 규격이 다른 후보는 무엇인가
- 어떤 workflow가 멈춰 있는가

이 `Project Document Graph`가 장기적으로 AIARC의 중요한 제품 자산이 된다.

## 9. 왜 챗봇이 아니라 AX인가

전통적 DX는 종이·수기 업무를 디지털 시스템으로 옮기는 데 초점을 둔다.

```text
종이 / 엑셀
→ 시스템 입력
→ 저장 / 조회
```

AI 기능이 추가되면 OCR, 요약, 검색, 초안이 붙을 수 있다.

AIARC가 지향하는 AX는 한 단계 더 나아간다.

```text
문서 수신
→ 이해
→ 관계 연결
→ 작성
→ 요청
→ 회신 추적
→ 상태 갱신
→ 다음 행동
→ 최종 제출
```

핵심은 **AI가 답변하는 것보다 workflow의 다음 단계를 실제로 전진시키는 것**이다.

## 10. Korea-first: 가장 복잡한 환경부터 깊게 해결한다

AIARC는 해외 범용성에 맞추기 위해 한국 제품을 얕게 만들지 않는다.

국내 건축·건설 환경에는 다음이 겹쳐 있다.

- HWP 중심 법정·업무 서식
- 국내 건축·건설 법령과 제출절차
- 감리·시공·건축주·자재업체 간 메일 업무관행
- 기관·발주처별 제출구조
- Windows 중심 사무환경
- 서명·날인과 버전 왕복

이 환경은 제품개발을 어렵게 만들지만 동시에 **해결할 가치가 있는 로컬 난이도**이기도 하다.

> **한국의 HWP와 국내 법정서식이라는 가장 복잡하고 특수한 업무환경부터 깊게 해결한다.**

이는 단순한 국내시장 한정 선언이 아니다. 하나의 시장에서 실제 workflow를 깊게 해결해 문서 이해, 관계 연결, 실행, 감사·근거 레이어를 축적하는 전략이다.

## 11. 왜 작게 시작하는가

최종 그림은 크다.

```text
Windows 폴더
+ 이메일
+ HWP
+ 문서이해
+ Document Graph
+ 생성
+ Workflow engine
+ 버전관리
+ 관계자 communication
+ 준공/자재승인/검측/기성 등 다수 업무
```

이 전체를 처음부터 완성하려 하면 문제 검증보다 개발이 앞서게 된다.

그래서 첫 프로토타입의 질문은 하나다.

> **실제 건설현장 자료를 AIARC가 읽고, 사람이 하던 문서정리와 다음 업무의 일부를 눈에 보이게 대신할 수 있는가?**

이를 보여주기 위해 1차는 다음으로 제한한다.

1. 준공 폴더 자동정리
2. 확보/누락/확인 필요 체크
3. 품질관리서 workflow 시각화
4. 최소 1개 문서생성 결과
5. 누락자료 요청메일 생성

HWP 완전자동화, 실시간 메일 agent, 다중회사 권한, 온프레미스 AI는 장기 제품에서 삭제하는 것이 아니라 **초기 시연의 blocker에서 제외**한다.

---

## 12. Prototype과 실제 제품을 혼동하지 않는다

1차 심사·검증을 위해 제품 shell과 DemoEngine을 사용할 수 있다.

```text
UI
↓
Agent Interface
├─ DemoEngine
└─ RealAIEngine
```

DemoEngine은 제품의 장면을 빠르게 보여주기 위한 것이며, 구현되지 않은 기능을 실제 AI 기능처럼 포장하지 않는다.

공개 데모에는 `Prototype Demo` 또는 `Demo Mode`를 명확히 표시한다.

이 결정의 목적은 기술을 속이는 것이 아니라 **아이디어의 핵심 workflow를 먼저 검증하고, 실제 integration을 단계적으로 붙이기 위해서**다.

## 13. 장기 그림: 20~30년 사업으로 본다

AIARC의 사업계획은 단기 준공앱 하나로 끝나지 않는다.

```text
준공서류 Prototype
→ 품질관리서 / 자재증빙 Agent
→ Closeout Agent
→ 자재승인 / 검측
→ Construction Document Graph
→ Multi-project / Team
→ Construction Backoffice AX
→ 국내 Architecture Document AX Platform
```

장기적으로 문서의 공통 생명주기는 다음 엔진으로 수렴한다.

```text
수집
→ 이해
→ 관계 연결
→ 생성
→ 검토
→ 전달
→ 회신 추적
→ 버전 관리
→ 제출
```

국내에서 이 엔진을 충분히 깊게 만든 뒤, 장기적으로 국가별 문서·법규·업무체계를 별도 workflow pack으로 다시 설계할 수 있다.

다만 글로벌은 현재 실행전략이 아니다. **국내 제품과 고객 문제를 깊게 해결하는 것이 우선**이다.

---

## 14. 현재 제품 정의

지금의 AIARC는 다음과 같이 정의한다.

> **AIARC는 건설회사의 기존 메일·Windows 폴더·HWP 환경 위에서 문서를 이해하고 정리하며, 필요한 문서를 작성하고, 관계자 요청과 회신·최신본을 추적하여 최종 제출물까지 이어주는 local-first 건설 공무 AI 앱이다.**

제품의 핵심은 파일을 예쁘게 정리하는 것이 아니라:

> **문서가 만들어지고, 전달되고, 확인되고, 수정되고, 최종 제출될 때까지의 전체 lifecycle을 실행 가능한 workflow로 바꾸는 것**

이다.

## 15. 변하지 않아야 할 원칙

1. 제품 때문에 새로운 반복 입력업무를 만들지 않는다.
2. 기존 Windows·메일·HWP 환경을 존중한다.
3. 단순 저장·검색보다 workflow 완료를 목표로 한다.
4. AI 판단과 원문 근거를 연결한다.
5. 법적·기술적 최종책임은 사람이 유지한다.
6. 하나의 실제 업무를 끝까지 해결한 뒤 확장한다.
7. 사람이 직접 추적·복붙·분류하는 시간을 우선 제거한다.
8. 프로토타입의 기술적 타협을 장기 제품정의와 혼동하지 않는다.
9. 한국의 복잡한 업무환경을 피하지 않고 제품의 핵심 경쟁력으로 만든다.
10. 장기 비전은 크게 보되, 다음 단계는 항상 검증 가능한 크기로 만든다.
