# AIARC 문제 인식과 설계 발전과정

Updated: 2026-09-04

이 문서는 AIARC가 어떤 문제에서 출발했고, 왜 현재의 `건설 공무 AI 에이전트` 설계로 발전했는지를 기록한다.

제품 기능 목록보다 **왜 이런 구조가 되었는가**를 보존하는 것이 목적이다.

---

## 1. 시작점: 건설 공무는 필수지만 사람에게 붙어 있는 업무다

초기 문제 인식은 단순했다.

건설회사에는 착공, 자재승인, 검측, 기성, 설계변경, 준공 등 프로젝트 전 과정에서 많은 공무업무가 발생한다. 규모가 큰 회사는 직원이 이 업무를 수행하지만, 소규모 회사나 프로젝트가 불규칙한 회사는 상시 전문인력을 두기 어렵다.

시장에는 실제로 착공서류, 자재승인원, 공정보고, 기성서류, 준공서류 등을 대신 작성하는 공무대행 서비스가 존재한다. 이는 건설 공무가 단순한 불편이 아니라 **실제 돈을 지불하고 해결하는 문제**임을 보여준다.

그러나 여기서 첫 번째 한계가 나타났다.

> 공무업무 전체를 사람 대신 맡아주는 서비스는 결국 또 하나의 인력집약적 공무대행 회사가 될 수 있다.

기성, 설계변경, 현장 상황 판단처럼 전문가의 경험과 현장맥락이 많이 필요한 업무를 전부 서비스화하면 확장성이 떨어질 수 있다.

따라서 질문을 바꿨다.

> **공무업무 전체를 대신하는 것이 아니라, 직원이 반복적으로 시간을 쓰지만 AI와 소프트웨어가 크게 줄일 수 있는 부분은 어디인가?**

---

## 2. 첫 번째 좁힘: 문서업무

건설 공무를 실제 업무 단위로 분해하면 반복되는 공통점이 있었다.

- 자료를 받는다.
- 파일을 읽는다.
- 어느 현장/공종/자재 자료인지 판단한다.
- 정해진 폴더에 넣는다.
- 누락된 자료가 무엇인지 확인한다.
- 회사나 법정양식을 작성한다.
- 관련 업체, 감리, 설계사 등에게 보낸다.
- 수정/날인본을 다시 받는다.
- 최신본을 찾아 교체한다.
- 최종 제출 시 다시 전체를 대조한다.

이 업무는 `전문가 판단`과 `문서 운영`이 섞여 있지만, 상당 부분은 **문서의 수집·분류·작성·전달·추적**이다.

여기서 AIARC의 첫 번째 형태가 나왔다.

> **건설 서류를 자동으로 정리해주는 AI**

## 3. 실제 준공폴더를 보면서 문제의 크기가 명확해졌다

준공서류 세트는 단순히 PDF 몇 개를 모아두는 폴더가 아니다.

현장에 따라 수십 개의 제출 항목이 있고, 각 항목 안에도 시험성적서, 납품확인서, 인증서, 사진, 확인서, 도면, 결과보고서 등이 묶인다.

예를 들어 최종 폴더는 다음과 같은 형태를 가질 수 있다.

```text
00. 준공도면
01-1. 준공사진첩
01-2. 지적측량결과부
02. 자재공급원승인요청서
03. 공사추진 실적 및 설계변경 총괄
...
23. 에너지 관련서류
24. 바닥타일
...
27. 에너지효율등급 인증서
```

문제는 최종 준공 시점에 갑자기 생기지 않는다.

공사기간 내내 이메일과 현장폴더에 자료가 쌓이다가, 준공 때 사람이 다시 찾아서 맞추고 누락을 보완한다.

따라서 더 좋은 제품 질문은 다음이 되었다.

> **준공 때 정리하는 것이 아니라, 공사 중에 들어오는 순간부터 AI가 준공 가능한 상태로 계속 유지하면 어떨까?**

이 시점부터 AIARC는 `준공서류 생성기`가 아니라 **지속적으로 문서 상태를 유지하는 프로그램**으로 바뀌었다.

## 4. 두 번째 전환: 새 SaaS가 아니라 기존 메일과 폴더 위에서 동작해야 한다

건설회사에 새로운 웹사이트를 주고 모든 자료를 다시 업로드하도록 요구하면 업무를 줄이는 대신 또 다른 업무를 만든다.

실제 자료는 이미 다음 공간에 있다.

```text
Outlook / Gmail
Windows 현장폴더
회사 공유폴더
다운로드 폴더
HWP / PDF / Excel / 이미지 / 도면
```

따라서 제품 원칙이 정해졌다.

> **사용자가 원래 하던 대로 메일을 쓰고 폴더에 저장하면, AIARC가 그 위에서 동작한다.**

이것이 `local-first` 방향의 출발점이다.

local-first는 단순한 보안 마케팅 문구가 아니다.

- 기존 Windows 업무방식과 맞는다.
- 대용량 도면/현장자료를 새 클라우드에 전부 이관하지 않아도 된다.
- 회사 내부 파일구조를 유지할 수 있다.
- HWP와 한컴오피스 같은 Windows 중심 도구와 자연스럽게 연결된다.

## 5. 세 번째 전환: 정리만으로는 부족하다

초기에는 받은 자료를 자동 분류하는 것만으로도 제품가치가 있다고 보았다.

하지만 건설 공무에는 **외부에서 받는 문서만큼 회사가 직접 작성해야 하는 문서가 많다.**

특히 건축 분야의 법정·기관·회사 양식은 HWP가 사실상 표준적인 작성환경으로 사용되는 경우가 많다.

예:

- 품질관리서
- 각종 확인서
- 준공 관련 서식
- 자재 관련 서식
- 착공/사용승인 관련 작성자료

현장명, 주소, 건축주, 시공사, 감리자, 공사기간 등 같은 데이터를 여러 문서에 반복해서 입력한다.

그래서 제품 범위가 다음처럼 확장되었다.

```text
정리
+
문서 생성
```

이때 중요한 설계원칙도 생겼다.

> AI가 백지에서 법정문서를 마음대로 쓰는 것이 아니라, **실제 사용하는 HWP 양식에 신뢰 가능한 현장데이터와 증빙에서 추출한 값을 채우는 방식**이 우선이다.

## 6. 품질관리서가 첫 번째 완성형 AX workflow를 보여줬다

제품의 방향을 결정적으로 바꾼 사례가 「건축법 시행령」 제62조의 품질관리서 업무였다.

현재 제62조는 대상 건축자재의 품질관리서가 다음과 같이 전달·확인되는 흐름을 규정한다.

```text
제조업자
→ 유통업자
→ 공사시공자
→ 공사감리자
→ 건축주
→ 사용승인 신청 시 허가권자
```

법령 참고: https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1025183813

현장 실무에서는 HWP 서식에 관계자 확인/날인을 거치기 위해 문서를 이메일로 주고받고, 각 회신본을 이어받아 최종본을 만드는 흐름이 일반적으로 발생한다.

사람은 그 과정에서 다음을 기억해야 한다.

- 지금 누구까지 확인했는가
- 누구에게 보냈는가
- 회신이 왔는가
- 첨부파일이 이전본인지 최신본인지
- 다음 사람에게 보내야 하는가
- 납품확인서/시험성적서 등 관련 증빙이 같이 있는가
- 최종본은 어느 파일인가

이것은 단순 문서보관 문제가 아니다.

**문서가 상태를 갖고 이동하는 workflow 문제**다.

그래서 AIARC의 제품정의가 다시 바뀌었다.

```text
정리
+
생성
+
메일 실행
+
회신 추적
+
버전/상태 관리
```

이때부터 `AI 파일정리`가 아니라 `AI Agent`라는 표현이 적합해졌다.

## 7. 메일은 부가기능이 아니라 workflow의 운송수단이다

기존 제품에서는 이메일을 `메일 보내기 기능` 정도로 생각하기 쉽다.

AIARC에서는 역할이 다르다.

```text
AIARC가 문서 상태 판단
→ 다음 관계자에게 보낼 문서 선택
→ 요청 메일 작성
→ 사용자 확인 후 발송
→ 회신 thread 감지
→ 첨부파일 인식
→ 기존 문서와 관계 판단
→ workflow 상태 갱신
→ 다음 행동 제안
```

즉 이메일은 AIARC 안에서 **문서 업무가 다음 단계로 이동하는 transport layer**다.

이 구조는 외부 회사가 AIARC를 설치하지 않아도 workflow에 참여할 수 있다는 장점도 있다.

제조사, 자재업체, 감리단, 설계사는 기존 이메일만 사용해도 된다.

## 8. Document Graph 개념

파일 중심 프로그램은 다음처럼 본다.

```text
폴더 A
  20260901_성적서.pdf
  납품확인서_최종.pdf
  품질관리서_rev4.hwp
```

AIARC가 지향하는 구조는 다르다.

```text
대흥동 현장
└─ 외벽 단열재
   ├─ 제조업자: A사
   ├─ 유통업자: B사
   ├─ 제품/규격
   ├─ 시험성적서
   ├─ 납품확인서
   ├─ 품질관리서
   │  ├─ Rev.1
   │  ├─ 제조 확인본
   │  ├─ 유통 확인본
   │  ├─ 시공 확인본
   │  └─ 감리 회신 대기
   ├─ 관련 이메일 thread
   └─ 준공 제출상태
```

이렇게 문서, 자재, 관계자, 이메일, workflow 상태를 연결하면 다음 질문에 답할 수 있다.

- 최신 승인본이 무엇인가
- 아직 회신을 못 받은 문서는 무엇인가
- 준공에 필요한데 없는 자료는 무엇인가
- 특정 자재의 시험성적서와 납품확인서 규격이 같은가
- 감리에게 보냈지만 답이 없는 문서는 무엇인가
- 이 현장의 준공 준비상태는 어느 정도인가

이 `Project Document Graph`가 장기적으로 AIARC의 중요한 데이터 자산이 될 수 있다.

## 9. 왜 AX인가

AIARC는 단순 DX와 구분된다.

### 전통적 DX

```text
종이/엑셀 업무
→ 웹 시스템에 입력
→ 디지털로 저장/조회
```

### AI 기능 추가

```text
기존 시스템
+
OCR / 요약 / 검색 / 초안
```

### AIARC가 지향하는 AX

```text
문서 수신
→ 이해
→ 관계 연결
→ 정리
→ 누락 판단
→ 문서 작성
→ 관계자 요청
→ 회신 추적
→ 최신본 반영
→ 다음 단계 수행
→ 최종 제출물 완성
```

사람이 하던 workflow의 일부를 AI가 실제로 이어받는 것이기 때문에 `건설 공무 AX`라는 정의가 적합하다.

## 10. 왜 지금인가

### 10.1 AI 문서이해 능력의 현실화

OCR, 문서 파싱, 대규모언어모델을 조합하면 비정형 파일에서 문서 종류와 핵심정보를 추출하고 서로의 관계를 추론하는 비용과 난이도가 빠르게 낮아지고 있다.

AIARC는 새로운 기반모델을 개발하는 사업이 아니라, 이미 사용 가능한 기술을 건설 공무 workflow에 맞게 조립하는 응용제품이다.

### 10.2 정책 타이밍

2026년 8월 국토교통부와 한국건설기술연구원 스마트건설지원센터는 **건설기업 DX·AX 전환 지원사업** 기획을 위한 수요조사를 진행했다.

공개 안내는 건설기업의 업무·데이터·시스템 활용현황과 DX·AX 수요를 파악하여 기업별 솔루션 구축·도입 지원방안을 마련하는 것을 목적으로 설명한다. AX의 예시에도 AI 기반 문서 작성·검토와 업무수행 지원이 포함된다.

참고: https://gyeongnam.kosca.or.kr/bbs/view.do?bbsId=BBS000482&menuId=MENU002987&nttNo=17654

이는 AIARC의 개별 구매수요를 직접 증명하는 자료는 아니다. 다만 **한국 건설업의 문서·업무 AX가 정책적으로도 현재 문제영역으로 인식되고 있다는 timing signal**이다.

### 10.3 한국 특화 진입장벽

해외 construction AI 제품이 발전하더라도 한국 현장에는 다음 로컬 맥락이 있다.

- HWP 법정/업무 서식
- 국내 건축·건설 법령과 제출절차
- 국내 감리/시공/자재업체 간 이메일 업무관행
- 국내 기관/발주처별 제출구조
- Windows 중심 사무환경

AIARC는 범용 AI를 한국 건설업에 단순 번역하는 것이 아니라 **이 로컬 workflow 자체를 제품화**한다.

## 11. 제품 범위를 작게 시작해야 하는 이유

AIARC의 최종 그림은 크다.

```text
메일 감시
+ Windows 폴더
+ HWP
+ 문서이해
+ Document Graph
+ 생성
+ workflow engine
+ 버전관리
+ 관계자 communication
+ 준공/기성/자재승인 등 다수 업무
```

이 전체를 첫 제품에서 완성하면 검증 전에 개발비와 시간이 과도하게 커진다.

따라서 첫 프로토타입의 질문은 다음 하나면 충분하다.

> **실제 건설현장 자료를 AI가 읽고, 사람이 하던 문서정리와 다음 업무 일부를 눈에 보이게 대신할 수 있는가?**

이를 증명하기 위해 첫 프로토타입은:

1. 준공 폴더 자동정리
2. 준공 누락/확인필요 체크
3. 품질관리서 workflow 시각화
4. 최소 1개 문서생성
5. 누락자료 요청메일 생성

정도로 제한한다.

HWP 완전자동화, 실시간 메일 agent, 다중회사 권한, 온프레미스 AI 등은 **제품의 장기 핵심에서 삭제하는 것이 아니라 프로토타입의 선행조건에서 제외**한다.

## 12. 최종적으로 도달한 제품 정의

아이디어의 변화는 다음과 같았다.

```text
건설 공무대행
↓
공무업무 중 문서 자동화
↓
건설 서류 자동정리 AI
↓
메일 + 기존 폴더를 읽는 local-first AI
↓
HWP 문서 생성 추가
↓
품질관리서의 법정 전달/확인 workflow 발견
↓
메일 회신 + 날인본 + 버전 추적 추가
↓
문서 생명주기를 수행하는 AI Agent
↓
Construction Backoffice AX
```

현재의 AIARC 정의:

> **AIARC는 건설현장의 기존 메일과 폴더 위에서 문서를 이해하고 정리하며, 필요한 HWP/업무 문서를 작성하고, 관계자에게 요청하고, 회신과 최신본을 추적하여 최종 제출물까지 이어주는 건설 공무 AI 에이전트다.**

---

## 13. 변하지 않아야 할 설계 원칙

제품이 커져도 다음 원칙은 유지한다.

1. 새로운 입력업무를 만들지 않는다.
2. 기존 메일/폴더/HWP 환경을 존중한다.
3. 단순 저장보다 workflow 완료를 목표로 한다.
4. 법적·기술적 책임판단은 사람이 유지한다.
5. AI의 추정과 원문근거를 연결한다.
6. 하나의 실제 업무를 끝까지 자동화한 뒤 확장한다.
7. 사람을 완전히 제거하는 것보다 **사람이 직접 추적하고 복붙하고 정리하는 시간을 제거**하는 데 집중한다.
8. 프로토타입의 기술적 타협을 장기 제품정의와 혼동하지 않는다.
