# AIARC 문제 인식과 설계 발전과정

Updated: 2026-09-04

이 문서는 AIARC가 어떤 문제에서 출발했고, 왜 지금의 제품 구조에 도달했는지를 기록합니다.

기능 목록보다 중요한 것은 **문제를 어떻게 발견했고, 제품 정의를 어떤 순서로 좁히고 깊게 만들었는가**입니다.

---

## 1. 시작점: 공무업무는 필수지만 많은 과정이 사람의 기억과 반복작업에 의존한다

건설 프로젝트에는 착공, 자재승인, 검측, 기성, 설계변경, 준공·사용승인 등 다양한 공무업무가 발생합니다.

규모가 큰 회사는 전담 인력이 이를 수행할 수 있지만, 소규모 회사나 프로젝트가 불규칙한 조직은 상시 전문인력을 두기 어렵습니다. 시장에 착공·준공·자재승인·설계변경 서류 등을 대신 작성하는 공무대행 서비스가 존재한다는 사실도 이 업무가 단순한 불편을 넘어 **실제 비용을 지불해 해결하는 문제**임을 보여줍니다.

하지만 여기서 첫 번째 한계가 보였습니다.

> **공무업무 전체를 사람 대신 맡아주는 방식은 결국 또 하나의 인력집약적 대행사업이 될 수 있다.**

기성률, 설계변경, 현장상황 판단처럼 경험과 책임이 중요한 업무까지 모두 자동화하려 하면 제품 범위가 지나치게 커지고 신뢰·책임 문제도 커집니다.

그래서 질문을 바꿨습니다.

> **사람의 전문판단은 남기되, 반복되는 문서 운영은 어디까지 소프트웨어가 끝낼 수 있을까?**

---

## 2. 첫 번째 좁힘: 공무 전체가 아니라 문서 업무 흐름

건설 공무를 실제 행동 단위로 나누면 반복되는 패턴이 보였습니다.

```text
자료를 받는다
→ 읽는다
→ 어느 현장·공종·자재인지 판단한다
→ 관련 자료와 연결한다
→ 폴더에 넣는다
→ 누락을 확인한다
→ 회사·법정서식을 작성한다
→ 관계자에게 보낸다
→ 회신을 받는다
→ 최신본을 교체한다
→ 최종 제출 때 다시 전체를 대조한다
```

이 과정에는 전문판단도 포함되지만 상당 부분은 **수집·분류·작성·전달·추적·정리**입니다.

AIARC의 첫 형태는 여기서 시작했습니다.

> **건설 서류를 자동으로 정리해주는 AI**

하지만 곧 `정리`만으로는 문제의 절반밖에 해결하지 못한다는 점이 드러났습니다.

---

## 3. 실제 준공서류 구조가 문제의 크기를 보여줬다

실제 준공 세트는 PDF 몇 개를 한 폴더에 넣는 수준이 아닙니다.

현장에 따라 준공도면, 사진첩, 측량자료, 자재승인원, 품질시험성과, 각종 검사필증, 폐기물처리확인서, 에너지 관련서류, 건축자재 품질관리서, 시험성적서와 납품확인서 등 **수십 종류의 제출 항목**이 생깁니다.

여기서 중요한 사실을 확인했습니다.

> **준공 문제는 준공 직전에 시작되지 않는다.**

공사기간 내내 이메일과 현장 폴더에 자료가 쌓이고, 같은 문서도 버전과 관계자 확인 상태가 계속 바뀝니다. 준공 직전이 되면 사람이 그동안 쌓인 자료를 다시 찾아 맞추고 빠진 자료를 요청합니다.

그래서 제품 질문이 달라졌습니다.

> **준공 때 한 번 정리하는 것이 아니라, 공사 중 자료가 들어오는 순간부터 계속 ‘준공 가능한 상태’를 유지할 수 없을까?**

이 지점에서 AIARC는 `준공서류 생성기`가 아니라 **지속적으로 문서 상태를 관리하는 앱**으로 발전했습니다.

---

## 4. 두 번째 전환: 새 SaaS가 아니라 기존 업무환경 위에서 작동해야 한다

건설회사에 새 웹서비스를 주고 모든 자료를 다시 올리라고 하면 업무를 줄이는 대신 또 하나의 입력업무를 만들 수 있습니다.

실제 자료는 이미 다음 공간에 존재합니다.

```text
Outlook / Gmail
Windows 현장 폴더
회사 공유폴더
다운로드 폴더
HWP / PDF / Excel / 이미지 / 도면
```

그래서 제품 원칙이 정해졌습니다.

> **사용자가 원래 하던 대로 메일을 쓰고 폴더에 저장하면 AIARC가 그 위에서 일한다.**

이것이 local-first 방향의 출발점입니다.

여기서 local-first는 단순한 보안 문구가 아닙니다.

- 기존 Windows 업무방식과 맞습니다.
- 대용량 현장자료를 새 클라우드로 전부 옮기지 않아도 됩니다.
- 회사 내부 폴더구조를 유지할 수 있습니다.
- HWP와 한컴오피스 같은 국내 실무도구에 더 자연스럽게 연결할 수 있습니다.

즉 AIARC는 사용자를 새로운 시스템 안으로 끌어들이기보다, **기존 도구들 사이에 AI 실행 레이어로 들어가는 제품**을 지향합니다.

---

## 5. 세 번째 전환: 받은 문서뿐 아니라 작성하는 문서까지

건설 공무에는 외부에서 받는 자료만큼 직접 작성해야 하는 문서가 많습니다.

특히 국내 건축·건설 업무의 법정서식, 기관서식, 감리·회사 양식에는 HWP가 깊게 사용됩니다.

현장명, 주소, 건축주, 시공사, 감리자, 공사기간, 자재정보 같은 값을 여러 문서에 반복해서 입력하는 경우도 많습니다.

그래서 제품 범위가 다음처럼 확장됐습니다.

```text
정리
+
문서 생성
```

동시에 중요한 경계를 세웠습니다.

> **AI가 법정문서를 백지에서 임의로 작성하는 것이 아니라, 실제 사용하는 서식에 신뢰 가능한 현장정보와 증빙에서 추출한 값을 채우는 방식이 우선이다.**

이 원칙은 지금도 유지합니다.

---

## 6. 품질관리서가 ‘문서 생명주기’ 문제를 선명하게 만들었다

「건축법 시행령」 제62조는 대상 건축자재의 품질관리서가 공급·시공·감리 단계를 거쳐 건축주와 허가권자 제출로 이어지는 구조를 규정합니다.

```text
제조업자
→ 유통업자
→ 공사시공자
→ 공사감리자
→ 건축주
→ 사용승인 신청 시 허가권자
```

법령 참고: https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1025183813

실무에서는 관련 서식과 증빙이 이메일로 오가며 확인본, 수정본, 날인본이 누적될 수 있습니다.

사람은 그 과정에서 계속 다음을 기억해야 합니다.

- 지금 어느 단계인가
- 누구에게 보냈는가
- 회신이 왔는가
- 받은 파일이 최신본인가
- 관련 증빙이 모두 있는가
- 다음 사람에게 보내야 하는가
- 최종본은 무엇인가

이 순간 문제는 `파일관리`보다 더 정확하게 정의됐습니다.

> **문서가 상태를 갖고 이동하는 업무 흐름의 문제다.**

그래서 AIARC는 다음 구조로 발전했습니다.

```text
정리
+
생성
+
메일 실행
+
회신 추적
+
버전·상태 관리
+
최종 제출
```

## 7. 이메일은 부가기능이 아니라 업무 흐름의 전달 수단이다

AIARC에서 이메일은 단순한 `메일 보내기 기능`이 아닙니다.

```text
문서 상태 판단
→ 다음 관계자 결정
→ 보낼 문서 선택
→ 요청메일 작성
→ 사용자 확인
→ 발송
→ reply·thread 감지
→ 첨부파일 인식
→ 기존 문서와 연결
→ 상태 갱신
→ 다음 행동
```

이 설계에는 중요한 장점이 있습니다.

**외부 관계자가 AIARC를 설치하지 않아도 됩니다.**

제조사, 자재업체, 감리단, 설계사 등은 기존 이메일을 그대로 쓰고, AIARC 사용자의 앱이 그 회신을 업무 흐름 안으로 가져올 수 있습니다.

---

## 8. 파일목록에서 Project Document Graph로

파일 중심 프로그램은 다음처럼 봅니다.

```text
현장 폴더
├─ 시험성적서.pdf
├─ 납품확인서_최종.pdf
└─ 품질관리서_rev4.hwp
```

AIARC가 지향하는 구조는 다릅니다.

```text
Project
└─ 외벽 단열재
   ├─ 제조업자
   ├─ 유통업자
   ├─ 제품·규격
   ├─ 시험성적서
   ├─ 납품확인서
   ├─ 품질관리서
   │  ├─ Rev.1
   │  ├─ 제조 확인본
   │  ├─ 유통 확인본
   │  ├─ 시공 확인본
   │  └─ 감리 회신 대기
   ├─ 관련 Email thread
   └─ 준공 제출상태
```

문서, 자재, 관계자, 메일, 버전, 업무 상태를 연결하면 다음 질문에 답할 수 있습니다.

- 최신 승인본은 무엇인가
- 감리에게 보냈지만 답이 없는 문서는 무엇인가
- 준공에 필요한데 아직 없는 자료는 무엇인가
- 같은 자재의 증빙끼리 규격이 다른 후보는 무엇인가
- 어떤 업무 흐름이 멈춰 있는가

이 `Project Document Graph`는 장기적으로 AIARC의 중요한 제품 자산이 될 수 있습니다.

## 9. 왜 챗봇이 아니라 AX인가

전통적 DX는 종이·수기 업무를 디지털 시스템으로 옮기는 데 초점을 둡니다.

```text
종이 / 엑셀
→ 시스템 입력
→ 저장 / 조회
```

여기에 AI가 더해지면 OCR, 요약, 검색, 초안 작성 같은 기능을 붙일 수 있습니다.

AIARC가 지향하는 AX는 한 단계 더 나아갑니다.

```text
문서 수신
→ 이해
→ 관계 연결
→ 작성
→ 요청
→ 회신 추적
→ 상태 갱신
→ 다음 행동
→ 최종 제출
```

핵심은 **AI가 답변하는 것보다 업무의 다음 단계를 실제로 전진시키는 것**입니다.

## 10. Korea-first: 복잡한 환경부터 깊게 해결한다

AIARC는 해외 범용성에 맞추기 위해 한국 제품을 얕게 만들지 않습니다.

국내 건축·건설 환경에는 다음 요소가 겹쳐 있습니다.

- HWP 중심 법정·업무 서식
- 국내 건축·건설 법령과 제출절차
- 감리·시공·건축주·자재업체 사이의 이메일 업무관행
- 기관·발주처별 제출구조
- Windows 중심 사무환경
- 서명·날인과 반복적인 버전 왕복

이 환경은 제품개발을 어렵게 만들지만, 바로 그 때문에 깊게 해결할 가치가 있습니다.

> **HWP와 국내 법정서식처럼 복잡하고 특수한 한국의 업무환경부터 깊게 해결한다.**

이는 단순히 국내시장에 머물겠다는 선언이 아닙니다. 하나의 시장에서 실제 업무를 끝까지 해결하며 문서 이해, 관계 연결, 실행, 근거·감사 레이어를 축적하는 전략입니다.

## 11. 왜 작게 시작하는가

최종 그림은 큽니다.

```text
Windows 폴더
+ 이메일
+ HWP
+ 문서 이해
+ Document Graph
+ 문서 생성
+ Workflow Engine
+ 버전 관리
+ 관계자 communication
+ 준공·자재승인·검측·기성 등 다수 업무
```

이 전체를 처음부터 완성하려 하면 문제 검증보다 개발이 앞서게 됩니다.

그래서 첫 프로토타입의 질문은 하나입니다.

> **실제 건설현장 자료를 AIARC가 읽고, 사람이 하던 문서정리와 다음 업무의 일부를 눈에 보이게 대신할 수 있는가?**

1차 프로토타입은 다음으로 제한합니다.

1. 준공 폴더 자동정리
2. 확보·누락·확인 필요 체크
3. 품질관리서 업무 흐름 시각화
4. 최소 1개 문서생성 결과
5. 누락자료 요청메일 생성

HWP 완전 자동화, 실시간 메일 에이전트, 다중회사 권한, 온프레미스 AI는 장기 제품에서 제거하는 것이 아니라 **초기 시연의 선행조건에서 제외**합니다.

---

## 12. 프로토타입과 실제 제품을 혼동하지 않는다

1차 심사와 검증을 위해 제품 shell과 DemoEngine을 사용할 수 있습니다.

```text
UI
↓
Agent Interface
├─ DemoEngine
└─ RealAIEngine
```

DemoEngine은 제품의 핵심 장면을 빠르게 보여주기 위한 도구입니다. 구현되지 않은 기능을 실제 AI 기능처럼 포장하지 않습니다.

공개 데모에는 `Prototype Demo` 또는 `Demo Mode`를 명확히 표시합니다.

이 결정의 목적은 기술을 과장하기 위해서가 아니라 **아이디어의 핵심 업무 흐름을 먼저 검증하고, 실제 연동을 단계적으로 붙이기 위해서**입니다.

## 13. 장기 그림: 20~30년 사업으로 본다

AIARC의 사업계획은 단기 준공앱 하나로 끝나지 않습니다.

```text
준공서류 Prototype
→ 품질관리서·자재증빙 Agent
→ Closeout Agent
→ 자재승인·검측
→ Construction Document Graph
→ Multi-project / Team
→ Construction Backoffice AX
→ 국내 Architecture Document AX Platform
```

장기적으로 문서의 공통 생명주기는 다음 엔진으로 수렴합니다.

```text
수집
→ 이해
→ 관계 연결
→ 생성
→ 검토
→ 전달
→ 회신 추적
→ 버전 관리
→ 제출
```

국내에서 이 엔진을 충분히 깊게 만든 뒤, 장기적으로 국가별 문서·법규·업무체계를 별도의 Workflow Pack으로 다시 설계할 수 있습니다.

다만 글로벌은 현재 실행전략이 아닙니다. **지금의 우선순위는 국내 사용자와 실제 업무를 깊게 해결하는 것**입니다.

## 14. 현재 제품 정의

현재 AIARC를 한 문장으로 정의하면 다음과 같습니다.

> **AIARC는 건설회사의 기존 이메일·Windows 폴더·HWP 환경 위에서 문서를 이해하고 정리하며, 필요한 문서를 작성하고, 관계자 요청과 회신·최신본을 추적해 최종 제출까지 이어주는 local-first 건설 공무 AI 앱이다.**

제품의 핵심은 파일을 보기 좋게 정리하는 것이 아닙니다.

> **문서가 만들어지고, 전달되고, 확인되고, 수정되고, 최종 제출될 때까지의 생명주기를 실행 가능한 업무 흐름으로 바꾸는 것**

입니다.

## 15. 변하지 않아야 할 원칙

1. 제품 때문에 새로운 반복 입력업무를 만들지 않습니다.
2. 기존 Windows·이메일·HWP 환경을 존중합니다.
3. 단순 저장·검색보다 업무 완료를 목표로 합니다.
4. AI 판단과 원문 근거를 연결합니다.
5. 법적·기술적 최종책임은 사람이 유지합니다.
6. 하나의 실제 업무를 끝까지 해결한 뒤 확장합니다.
7. 사람이 직접 추적·복사·붙여넣기·분류하는 시간을 우선 줄입니다.
8. 프로토타입의 기술적 타협을 장기 제품정의와 혼동하지 않습니다.
9. 한국의 복잡한 업무환경을 피하지 않고 제품 경쟁력으로 만듭니다.
10. 비전은 크게 보되, 다음 단계는 항상 검증 가능한 크기로 정합니다.
