# AIARC 건설 문서 생애주기 AX 설계

Updated: 2026-09-08
Status: Current product-design baseline

## 0. 문서 목적

AIARC는 단순한 건설 문서 분류기나 준공서류 정리기가 아니다.

AIARC가 장기적으로 다루려는 핵심 문제는 **건설 프로젝트에서 문서가 생성되고, 승인되고, 변경되고, 대체되고, 최종 제출본으로 확정되는 전체 생애주기**다.

제품 관점의 내부 정의:

> **AIARC = 건설 문서 생애주기 AX**

단, 이 표현은 제품 설계의 핵심 개념으로 사용한다. 외부 경진대회나 마케팅에서는 더 구체적이고 즉시 이해되는 문제/해결 훅을 우선할 수 있다.

---

## 1. 파일이 아니라 시간축이 있는 업무 객체

건설 문서는 파일 하나로 끝나지 않는다.

같은 종류의 문서도 공사 단계와 승인상태에 따라 의미가 달라진다.

```text
생성
→ 검토
→ 승인
→ 현장 반영
→ 변경
→ 재검토 / 재승인
→ 최신본 교체
→ 준공 반영
→ 최종 제출
```

따라서 AIARC는 문서를 단순히 `어떤 폴더에 들어가는 파일인가`로만 판단해서는 안 된다.

최소한 다음을 함께 이해해야 한다.

- 어느 현장에 속하는가
- 어느 공사 단계에서 필요한가
- 어떤 업무 목적을 가진 문서인가
- 현재 상태는 무엇인가
- 이전 버전과 어떤 관계인가
- 무엇을 대체하는가
- 어떤 승인 또는 확인을 거쳤는가
- 현재 유효한 최신본인가
- 준공 또는 최종 제출에 포함되는가
- 다른 문서와 어떤 관계를 가지는가

---

## 2. 단계별 필요 문서

문서가 존재한다고 해서 모든 공사 단계에서 필요한 것은 아니다.

예를 들어 자재승인원은 자재를 사용하기 전 승인단계에서 중요하지만, 일반적인 준공 제출세트의 핵심 문서로 그대로 들어가는 것은 아니다.

```text
착공 / 공사 초기
├─ 착공 관련 서류
├─ 자재승인원
├─ 자재 카탈로그
├─ 시험성적서 / 인증자료
└─ 초기 승인자료

공사 중
├─ 품질관리 관련 서류
├─ 납품확인서
├─ 시험성적서
├─ 검측 / 검수
├─ 시공사진
├─ 변경도면
└─ 각종 승인 / 회신자료

준공 / 사용승인
├─ 준공도면
├─ 최종 품질 관련 제출자료
├─ 감리 관련 최종자료
├─ 사용승인 관련 서류
├─ 최종 INDEX
└─ 현장별 최종 제출세트
```

정확한 문서범위는 프로젝트, 발주처, 법령, 감리, 공종에 따라 달라질 수 있으므로 고정 목록 하나로 모든 현장을 판정하지 않는다.

핵심은 **문서 종류 + 공사 단계 + 현장별 요구조건**을 함께 보는 것이다.

## 3. 도면 생애주기

도면은 AIARC의 문서 생애주기 개념을 가장 잘 보여주는 사례다.

허가도면으로 착공하더라도 실제 공사 중 현장조건, 설계변경, 자재변경, 관계자 협의 등으로 도면이 계속 수정될 수 있다.

예:

```text
A-101 평면도
├─ 허가도면
├─ 착공본
├─ 현장 수정본
├─ 설계변경 검토본
├─ 설계변경 승인본
├─ 실제 시공 반영본
└─ 준공도면
```

AIARC는 단순히 모든 파일을 `도면` 폴더에 넣는 것이 아니라 다음 질문에 답할 수 있어야 한다.

- 같은 도면번호의 파일이 여러 개 있을 때 현재 최신본은 무엇인가
- 허가 이후 변경된 도면은 무엇인가
- 변경도면이 승인되었는가
- 현장에서 실제 반영된 버전은 무엇인가
- 설계변경 승인자료와 해당 도면이 연결되어 있는가
- 변경사항이 준공도면에 반영되었는가
- 오래된 도면이 현재 작업폴더에 섞여 있는가

장기적으로는 도면별 Revision Graph를 유지한다.

```text
Drawing
├─ Drawing No.
├─ Discipline
├─ Revision
├─ Date
├─ Status
├─ Approval state
├─ Supersedes
├─ Superseded by
├─ Related change request
└─ Final / as-built state
```

## 4. 자재 문서 생애주기

하나의 자재도 여러 문서와 여러 단계에 걸쳐 관리된다.

```text
자재 계획
↓
자재승인 자료 수집
↓
자재승인원 작성 / 제출
↓
승인 / 보완
↓
납품
↓
납품확인
↓
품질 / 시험 / 인증 증빙 연결
↓
시공 / 검측
↓
공사 중 변경 또는 대체자재 발생 가능
↓
최종 품질자료 정리
↓
준공 제출세트 편입 여부 판단
```

따라서 `자재승인원`, `시험성적서`, `납품확인서`, `품질관리서`를 단순히 항상 한 세트로 간주하지 않는다.

각 문서는 **언제 필요한지, 무엇을 증명하는지, 다음 단계에 어떤 영향을 주는지**를 별도로 관리한다.

## 5. Document Lifecycle 데이터 모델

기존 Project Document Graph는 시간축을 포함하도록 확장한다.

```text
Project
├─ Stages
├─ Parties
├─ Materials
├─ Work items
├─ Drawings
├─ Documents
├─ Email threads
├─ Revisions
├─ Approvals
├─ Change events
├─ Submission sets
└─ Workflow instances
```

### Document 핵심 속성

```text
Document type
Project
Stage
Work item / Material
Purpose
Original file
Source email / folder
Created date
Effective date
Revision
Status
Approval state
Supersedes
Superseded by
Related documents
Related change event
Extracted values
Evidence
Submission relevance
Final-state flag
```

### Status 예시

```text
수신
분류됨
검토 필요
작성 필요
검토 중
승인 요청
보완 요청
승인
현장 반영
변경 발생
구버전
최신본
준공 반영 필요
준공 반영 완료
최종 제출본
```

모든 문서종류가 모든 상태를 거치는 것은 아니다. 문서별 workflow schema를 사용한다.

## 6. AIARC가 해결해야 하는 네 가지 핵심 판단

### 6.1 Identity

`이 파일이 무엇인가?`

- 문서 종류
- 자재 / 공종
- 도면번호
- 현장
- 관계자

### 6.2 Stage

`이 문서는 언제 필요한가?`

- 착공
- 승인
- 공사 중
- 설계변경
- 품질 / 검측
- 준공
- 사용승인

### 6.3 State

`현재 어떤 상태인가?`

- 작성중
- 승인대기
- 승인
- 수정됨
- 구버전
- 최신본
- 최종본

### 6.4 Relation

`무엇과 연결되는가?`

- 이전 / 다음 버전
- 관련 자재
- 관련 도면
- 관련 공문
- 승인 근거
- 변경 근거
- 최종 제출세트

이 네 가지를 함께 알아야 문서 생애주기 AX가 가능하다.

## 7. 누락의 정의도 단계에 따라 달라진다

AIARC에서 `누락`은 단순히 기준 폴더에 파일이 없다는 뜻이 아니다.

예:

```text
착공단계
자재승인원이 없음
→ 업무 누락 가능성
```

```text
준공단계
자재승인원이 최종 제출폴더에 없음
→ 반드시 누락이라고 볼 수 없음
```

반대로:

```text
공사 중 설계변경 발생
→ 변경 승인본 존재
→ 준공도면에 변경내용 미반영
```

이면 문서는 모두 존재하지만 **생애주기상 누락**이다.

따라서 장기적으로 AIARC의 누락판정은:

```text
현재 공사단계
+ 업무 workflow
+ 현장별 요구조건
+ 문서 상태
+ 문서 관계
+ 최종 제출 요구조건
```

을 함께 사용해야 한다.

## 8. 버전과 최신본 관리

`최신 수정일 파일 = 최신본`으로 단순 판정하지 않는다.

가능한 근거:

- 문서 내부 revision
- 도면 revision
- 작성 / 발행일
- 승인일
- 이메일 회신 순서
- 파일명
- 변경 공문
- 승인번호
- 사용자 확정
- 동일 문서와의 내용 비교

AIARC는 근거를 종합해 `최신본 후보`를 제시하고, 확실하지 않은 경우 자동 확정하지 않는다.

안전 원칙:

> 최신본 판정은 파일 이동 편의를 위한 기능과 실제 공사·법적 효력을 가진 문서 확정을 구분한다.

법적·기술적 최종효력 판단이 필요한 경우 사람의 권한을 유지한다.

## 9. UI/UX 연결

문서 생애주기 AX는 UI를 복잡한 업무시스템으로 만들기 위한 명분이 아니다.

사용자에게는 여전히 단순하게 보여야 한다.

기본 UX:

```text
자료를 던진다
↓
AIARC가 분류 / 상태 / 버전 / 관계를 분석한다
↓
정상건은 자동 처리한다
↓
예외만 보여준다
↓
사용자가 필요할 때 근거를 본다
↓
딸깍
```

좌측 문서트리는 현재 현장의 구조를 보여주되, 필요하면 다음 상태를 시각적으로 표현할 수 있다.

```text
✓ 최신 / 완료
△ 확인 필요
● 진행 중
↻ 변경됨
○ 구버전
! 누락 / 미반영
```

정확한 시각언어는 APP_DESIGN 및 APP_CANVAS_UX에서 결정한다.

## 10. 초기 MVP와의 관계

`건설 문서 생애주기 AX`는 매우 넓은 장기 제품 정의다.

모두의 창업용 초기 MVP에서 전체 생애주기를 모두 구현하지 않는다.

초기 진입점:

> **준공 단계에서 뒤섞인 현장 문서를 자동정리하고, 필요한 문서·최신본·누락·불일치 후보를 찾아주는 경험**

이후 실제 제품은 시간을 거꾸로 확장한다.

```text
준공 정리
↓
공사 중 지속적인 준공 준비
↓
품질 / 자재 문서 workflow
↓
자재승인
↓
설계변경 / 도면 revision
↓
착공부터 준공까지 Continuous Document Lifecycle
```

준공은 제품의 끝이 아니라 **가장 눈에 보이는 첫 진입점**이다.

## 11. 제품 포지셔닝 원칙

내부 제품 정의:

> **건설 문서 생애주기 AX**

외부 설명에서는 이 문구만 단독으로 사용하지 않는다.

이유:

- 너무 넓게 들릴 수 있음
- 일반적인 `건설 업무 AX`와 차이가 즉시 드러나지 않을 수 있음
- 초기 사용자 문제를 한 번에 상상하기 어려울 수 있음

따라서 외부에서는 항상 구체적인 문제를 먼저 말한다.

예:

> 현장 폴더를 통째로 넣으면 AI가 준공에 필요한 서류를 정리하고, 빠진 문서와 잘못된 최신본 후보까지 찾아준다.

그 다음 확장 논리에서:

> 이를 시작으로 착공부터 설계변경, 품질관리, 준공까지 이어지는 건설 문서 생애주기 전체를 AX한다.

라고 설명한다.

## 12. 검증 방향

실제 현장자료를 이용한 첫 검증에서는 단순 분류 정확도만 측정하지 않는다.

가능한 검증축:

1. 문서 종류 판별
2. 공사 단계 판별
3. 자재 / 공종 귀속
4. 관련 문서 연결
5. 동일 문서 revision 연결
6. 최신본 후보 판별
7. 준공 관련성 판별
8. 현재 단계에서 필요한 문서 누락 후보 탐지
9. 변경 이후 최종본 미반영 탐지
10. 주요 필드 불일치 탐지

실제 사람이 정리한 폴더트리, 파일명, 완료표시, 버전관리 흔적은 ground truth 후보로 활용할 수 있다.

단, 사람이 만든 구조도 오류가 있을 수 있으므로 절대정답으로 가정하지 않고 필요 시 사람이 직접 라벨을 보정한다.

## 13. 장기 목표

AIARC의 최종 목표는 `건설 파일을 잘 찾아주는 프로그램`이 아니다.

```text
어떤 문서가 필요한가
→ 지금 어떤 상태인가
→ 무엇이 최신인가
→ 어떤 변경이 발생했는가
→ 무엇이 아직 반영되지 않았는가
→ 다음에 무엇을 해야 하는가
→ 최종 제출 가능한 상태인가
```

를 계속 이해하고 실행하는 것이다.

즉 AIARC의 장기 제품은 **건설 프로젝트 문서의 상태와 시간축을 기억하고 실행하는 AI 작업 레이어**다.
