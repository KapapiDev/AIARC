# AIARC Product Overview

AIARC는 **준공 단계의 반복적인 문서 정리·누락 확인·보완 업무를 줄이는 Windows 데스크톱 AI**에서 시작합니다.

현재 제품은 준공 문서 자동화이고, 다음 제품 단계는 **AI Project Workspace**입니다. 그 중심에는 프로젝트에서 **지금 무엇이 유효하고, 무엇이 바뀌었고, 무엇이 미결인지** 이해하는 `Project State`가 있습니다.

장기적으로는 건축 프로젝트의 더 넓은 지식업무를 수행하는 **Architecture AI**를 목표로 합니다.

```text
현재
준공 문서 자동화

↓

다음 제품
AI Project Workspace

↓

핵심 능력
Project State

↓

장기
Architecture AI
```

## 문제

건설 문서는 저장으로 끝나지 않습니다. 공사 중 계속 만들어지고, 검토되고, 수정되고, 보완되고, 최종본으로 확정됩니다.

준공 단계에서는 특히 다음 일이 반복됩니다.

- 전달받은 자료 확인
- 누락 확인
- 보완 요청
- 수정·보완본 수신
- 최신본 반영
- 변경사항의 최종 반영 여부 확인
- 제출 가능한 최종 세트 정리

자료가 잘 정리되어 오는 프로젝트도 있고 그렇지 않은 프로젝트도 있습니다. 문제는 특정 참여자의 정리 수준이 아니라, **여러 단계의 검토 사이에서 같은 자료를 다시 찾고 맞추고 보완하는 일이 반복된다는 것**입니다.

## 현재 제품

현재 0.6.0 프로토타입은 준공 단계에 이미 흩어져 있는 자료를 정리하는 제품 경험을 보여줍니다.

```text
현장 폴더 / ZIP
→ AIARC 분석
→ 문서 분류 · 관계 연결
→ 누락 · 중복 · 최신본 후보 · 확인 필요
→ 전체 정리
→ 예외와 원문 근거 확인
```

핵심 UX는 **자동화가 먼저 일하고, 사용자는 필요한 순간에만 확인하는 것**입니다.

## 왜 준공부터 시작하는가

준공 단계에는 프로젝트 전 과정에서 생성된 결과물이 모입니다. 그래서 문서 종류, 관계, 누락, 최신본, 변경 반영 여부를 한꺼번에 확인해야 합니다.

AIARC는 이 지점에서 먼저 다음 능력을 검증합니다.

- 문서가 무엇인지 이해하는가
- 어떤 업무·자재·공종과 연결되는지 파악하는가
- 최신본과 구버전 후보를 구분할 수 있는가
- 무엇이 빠졌는지 찾을 수 있는가
- 사용자가 처음부터 모든 파일을 다시 확인하는 시간을 줄일 수 있는가

준공 문서가 최종 목적이라서가 아니라, **AI가 실제 프로젝트 자료의 관계와 상태를 이해할 수 있는지 작게 검증하기 좋은 첫 진입점**이기 때문입니다.

## 다음 제품: AI Project Workspace

다음 단계에서는 준공 시점에 한 번 정리하는 것을 넘어, 프로젝트 자료가 계속 들어오는 동안 같은 프로젝트 맥락을 유지하는 **AI Project Workspace**로 확장합니다.

```text
문서 · 도면 · 메일 · 사진 · 변경 기록
                ↓
문서 자동 정리와 관계 파악
                ↓
Project State
현재 상태 · 변경 · 미결사항 · 근거
                ↓
Project AI
검색 · 질문 · 설명
                ↓
필요한 다음 업무로 연결
```

모든 참여자가 처음부터 새로운 플랫폼으로 이동해야만 가치가 생기는 구조로 시작하지 않습니다. 기존 폴더, ZIP, 이메일 중심의 업무환경을 존중하면서 한 명의 사용자가 먼저 가치를 얻을 수 있어야 합니다.

## 왜 Project State인가

건축 프로젝트의 실제 상태는 파일 하나에 들어 있지 않습니다.

예를 들어:

```text
원도면 A
→ 현장 변경지시
→ 수정도면 B
→ 회의록 / 메일
→ 실제 시공 / 현장사진
→ 관련 자재 발주
```

몇 달 뒤 사용자는 다음처럼 묻게 됩니다.

> **“이 부분 원래 이렇게 되어 있었어?”**  
> **“언제, 왜 바뀐 거야?”**

기존 파일 중심 환경에서는 사람이 흩어진 도면·회의록·메일·사진을 다시 찾아 기억을 복원해야 합니다.

AIARC가 지향하는 Project State는 **현재 상태뿐 아니라 변화의 흐름과 그 근거를 연결해 유지하는 것**입니다.

```text
원래 상태 A
→ 변경지시
→ 수정도면 B
→ 확인 기록
→ 실제 시공

현재 상태 B
+ 관련 근거
+ 남은 미결사항
```

따라서 AIARC의 Project AI는 단순한 파일검색이 아니라 다음 질문에 답하는 방향으로 발전합니다.

- 현재 유효한 문서와 도면은 무엇인가
- 무엇이 누락되었는가
- 무엇이 언제 바뀌었는가
- 왜 현재 상태가 되었는가
- 관련 근거는 어디에 있는가
- 지금 다음으로 무엇을 확인하거나 처리해야 하는가

내부적으로 이 방향을 **Project State Reconstruction → Next-action Execution**이라고 부릅니다.

## 차별화된 확장 workflow

AIARC의 확장 방향은 **준공 직전에 하는 정리를 공사 중으로 앞당기는 것**입니다.

```text
프로젝트 생성
→ 프로젝트 코드 / 초대 링크
        ↓
프로젝트에 필요한 역할의 참여자가 자료 추가
        ↓
AIARC 자동 분류 · 관계 연결 · 버전 관리
        ↓
누락 · 보완 · 최신 유효본 · 확인 필요 상태 갱신
        ↓
수정본 · 보완 결과 · 확인 결과 누적
        ↓
공사 완료
        ↓
누적된 유효 자료에서 준공 · 사용승인용 최종 세트 생성
```

전문가의 검토와 책임은 그대로 두고, AIARC는 그 전후에서 반복되는 **정리·누락 확인·보완 요청·수정본 반영·전달·추적**을 줄입니다.

> **건물을 짓는 동안, 준공서류도 함께 완성됩니다.**

프로젝트 코드나 공동 저장공간 자체가 차별점은 아닙니다. 핵심은 **자료가 생길 때부터 같은 프로젝트에 연결되고, AI가 프로젝트의 상태와 변화를 계속 이해하는 것**입니다.

## 초기 고객과 진입 전략

AIARC의 초기 고객은 건축·건설 프로젝트에서 문서를 직접 취합하고, 누락을 확인하고, 보완본과 최신본을 반영하는 실무자입니다. 창업자 역시 건축사사무소에서 감리·사용승인 업무에 참여하며 같은 작업을 직접 수행하고 있습니다.

초기 제품은 회사 전체의 업무방식을 바꾸거나 여러 참여자가 동시에 새로운 시스템에 들어와야만 가치가 생기는 구조로 시작하지 않습니다. 기존처럼 폴더, ZIP, 이메일로 자료를 전달받아도 AIARC 사용자 한 명이 자신의 PC에서 바로 문서 정리와 검토 업무를 줄일 수 있도록 설계합니다.

## 제품 원칙

- **Existing workflow first**: 기존 Windows 폴더·이메일·HWP 중심 환경을 존중
- **Local-first**: 원본과 현장 데이터는 가능한 한 사용자 PC·회사 저장소 중심
- **HWP-aware**: HWP/HWPX를 국내 업무환경의 핵심 형식으로 취급
- **Automation first**: 문제가 없는 문서는 자동 처리하고 예외만 사람에게 표시
- **Evidence before automation**: AI 판단을 가능한 한 원문 근거와 연결
- **Human authority remains**: 법적·기술적 최종 판단과 날인·서명은 사람이 수행

## 현재 제품과 다음 단계

### 현재 0.6.0

- 준공 문서 자동정리 제품 경험
- 폴더 / ZIP 투입
- 분류·관계·누락·중복·최신본 후보 표시
- 예외와 원문 근거 확인

### 다음 제품 검증

- AI Project Workspace
- 공사 중 자료 누적
- Project State
- 프로젝트에 대한 검색·질문·설명
- 변화와 근거의 연결
- 준공 시 재취합·재정리 감소

현재 프로토타입에서 구현된 것과 다음 제품 단계에서 검증할 것은 구분해 설명합니다.

## 장기 방향

```text
준공 문서 자동화
→ AI Project Workspace
→ Project State
→ Project Intelligence
→ Architecture / Construction Agent
→ Architecture AI
```

> **Architecture AI가 프로젝트를 수행하려면 먼저 프로젝트가 지금 어떤 상태인지 이해해야 합니다. AIARC는 그 상태를 실제 업무에서 먼저 만들고 검증합니다.**

큰 비전은 유지하되, 제품의 가치는 각 단계에서 실제 사용자와 실제 자료로 검증합니다.

상세 구현 방식, 데이터 모델, 평가체계와 내부 자동화 로직은 비공개 개발 저장소에서 관리합니다.
