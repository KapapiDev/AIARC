# AIARC 제품설계서

Updated: 2026-09-04

## 1. 제품 정의

**AIARC는 건설회사가 이미 사용하는 이메일, Windows 현장폴더, HWP 중심 문서환경 위에서 건설 서류를 이해하고 정리하고 생성하고 추적하여 최종 제출물까지 이어주는 local-first 건설 공무 AI 에이전트다.**

한 줄 정의:

> **받은 서류는 알아서 정리하고, 작성해야 할 서류는 만들어주고, 빠진 자료는 요청하고, 회신과 최신본을 추적하여 최종 제출 세트까지 완성하는 건설 Document AX.**

AIARC는 새로운 ERP를 중심으로 업무를 재입력하게 하는 제품이 아니다. 기존 업무공간인 `메일 + 현장 폴더 + 한글 문서`를 출발점으로 삼는다.

---

## 2. 해결하려는 문제

### 2.1 건설 공무의 문서는 파일이 아니라 업무 상태다

현장의 문서는 단순히 보관하면 끝나지 않는다.

하나의 자재나 공종을 기준으로 다음 자료가 서로 연결될 수 있다.

```text
자재
├─ 자재공급원 승인자료
├─ 품질관리서
├─ 납품확인서
├─ 시험성적서
├─ 품질인정/인증 자료
├─ 카탈로그/사양서
├─ 반입/시공 사진
├─ 검측/확인자료
└─ 최종 준공/사용승인 제출자료
```

각 자료는 이메일, 다운로드 폴더, 개인 PC, 현장 공유폴더 등에 분산되고 파일명이 일정하지 않다. 같은 문서가 여러 번 오가며 버전과 날인상태가 달라진다.

따라서 실제 업무는 다음을 포함한다.

- 이 문서가 어느 현장 자료인지 판단
- 어느 자재/공종과 연결되는지 판단
- 최신본인지 구분
- 관련 증빙이 모두 있는지 확인
- 문서끼리 제품명, 제조사, 규격 등의 정보가 일치하는지 확인
- 누락자료가 누구에게 있는지 파악
- 메일로 요청
- 회신을 받아 다음 단계로 넘김
- 최종본을 준공/사용승인 제출체계에 편입

### 2.2 작성문서는 HWP 중심이다

한국 건축·건설 실무의 법정서식과 기관·감리·회사 업무양식은 HWP 비중이 높다.

따라서 AIARC의 장기 제품은 단순 PDF OCR 제품이 아니라 **HWP 작성환경을 포함하는 Windows 업무 에이전트**여야 한다.

다만 첫 프로토타입의 목적은 상용 제품 전체를 완성하는 것이 아니다. HWP 자동화가 일정상 병목이 될 경우 화면상 생성, 제한된 템플릿 자동화 또는 수동 저장을 허용하고, HWP 완전통합은 초기 상용화 단계로 넘길 수 있다.

## 3. 법정 업무가 만드는 구조적 필요

AIARC의 초기 대표 workflow는 「건축법 시행령」 제62조의 **건축자재 품질관리서**다.

현재 법령은 대상 건축자재에 대해 품질관리서가 다음과 같이 전달·확인되는 흐름을 규정한다.

```text
제조업자
→ 유통업자
→ 공사시공자
→ 공사감리자
→ 건축주
→ 사용승인 신청 시 허가권자
```

- 제조업자는 품질관리서를 유통업자에게 제출한다.
- 유통업자는 품질관리서와 건축자재의 일치 여부 등을 확인한 뒤 시공자에게 전달한다.
- 시공자는 일치 여부를 확인한 뒤 해당 현장의 품질관리서 전체를 감리자에게 제출한다.
- 감리자는 감리완료보고서에 첨부하여 건축주에게 제출한다.
- 건축주는 사용승인 신청 시 허가권자에게 제출한다.

법령 참고: https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1025183813

현장 실무에서는 법정 HWP 서식의 관계자 확인·날인과 수정본이 이메일로 순차 왕복하며 최종본이 완성되는 경우가 많다.

따라서 이 업무의 핵심 문제는 단순 `파일 저장`이 아니라:

```text
작성
→ 증빙 연결
→ 관계자 확인/날인
→ 전달
→ 회신
→ 최신본 판별
→ 다음 관계자 전달
→ 최종본 확정
→ 제출자료 편입
```

이라는 workflow 관리다.

## 4. 목표 사용자

### 4.1 초기 사용자

- 중소·중견 건설사의 현장 공무 담당자
- 현장소장 또는 공무를 겸임하는 실무자
- 본사 공무/공사관리 담당자
- 전문건설업체의 서류 담당자

### 4.2 향후 사용자

- 감리단
- 건축사사무소/설계사
- 시행사/건축주 측 공사관리 조직
- 자재 제조·유통업체
- 공무대행/건설관리 전문업체

초기에는 모든 관계자가 AIARC 계정을 가져야 하는 구조를 피한다. 외부 관계자는 기존 이메일을 그대로 사용해도 workflow에 참여할 수 있어야 한다.

## 5. 제품의 핵심 원칙

### P1. Existing workflow first

사용자가 이미 사용하는 Outlook/Gmail, Windows 폴더, HWP를 최대한 유지한다.

새 시스템에 자료를 다시 업로드하고 분류하는 추가업무를 만들지 않는다.

### P2. Local-first

원본 파일과 현장별 인덱스는 가능한 한 사용자 PC 또는 회사 저장소를 중심으로 관리한다.

필요한 AI 추론만 외부 모델 API를 사용할 수 있으며, 상용화 단계에서 보안 요구에 따라 온프레미스/로컬 모델 선택지를 검토한다.

`local-first`는 반드시 `완전 오프라인`을 의미하지 않는다.

### P3. HWP-aware

HWP를 주변 호환기능이 아니라 한국 건설업의 핵심 문서환경으로 취급한다.

### P4. Workflow, not chatbot

질문에 답하는 것보다 다음 실제 업무를 끝내는 데 집중한다.

예:

- `누락자료 찾아줘`에서 끝나지 않고 요청 메일 초안까지 만든다.
- 회신이 오면 해당 문서의 다음 workflow 상태를 제안한다.
- 최종본이 되면 올바른 제출 폴더에 편입한다.

### P5. Evidence before automation

AI가 추출하거나 추정한 값에는 가능한 한 원문 근거 파일을 연결한다.

확신도가 낮은 내용은 자동 확정하지 않고 `확인 필요` 상태로 둔다.

### P6. Human authority remains

AIARC는 다음을 임의로 대신하지 않는다.

- 관계자의 실제 날인/서명
- 법적 최종판단
- 기술적 책임자의 최종 확인
- 설계변경 타당성의 최종판단
- 실제 기성률/공사수량의 책임판정

AI는 자료수집, 초안, 대조, 상태관리, 요청과 같은 반복업무를 줄인다.

### P7. Narrow workflow first

처음부터 모든 공무업무를 자동화하지 않는다.

하나의 workflow를 `입력 → 결과`까지 완성한 뒤 인접 업무로 확장한다.

## 6. AIARC의 다섯 가지 제품 능력

### 6.1 UNDERSTAND

메일과 파일을 읽고 의미를 구조화한다.

- 현장 판별
- 문서 종류 판별
- 공종/자재 판별
- 제조사/유통사/시공사/감리 등 관계자 추출
- 제품명/규격/날짜/번호 추출
- 관련 문서 연결

### 6.2 ORGANIZE

파일을 업무 구조에 맞게 정리한다.

- 표준 파일명 추천/변경
- 현장별 폴더 편입
- 준공 항목별 자동 분류
- 중복 탐지
- 최신본/구버전 판별 보조
- 문서 묶음 구성

### 6.3 CREATE

회사가 작성해야 하는 문서를 생성한다.

- 현장 마스터 데이터 자동 채움
- 기존 법정/회사 양식 기반 작성
- HWP 템플릿 자동화
- 목록, INDEX, 총괄표 작성
- 품질관리서 등 반복서식 작성 보조

### 6.4 ACT

필요한 다음 업무를 실행한다.

- 누락자료 요청 메일 초안
- 상대방/첨부파일 추천
- 사용자 확인 후 발송
- 후속 버전에서 자동 follow-up, 재요청, 단계 이동

### 6.5 TRACK

문서의 생명주기와 workflow 상태를 추적한다.

- 작성 필요
- 요청 전
- 요청 발송
- 회신 대기
- 관계자 확인 완료
- 다음 관계자 전달 필요
- 최종본
- 제출 완료

## 8. 대표 workflow A: 준공서류 자동 정리

### Input

- 실제 현장 폴더
- 준공서류 목록 또는 기준 폴더 구조
- 이메일에서 확보된 첨부자료

### Process

1. 파일 스캔
2. 문서 내용/파일명 기반 분류
3. 준공 요구항목 매칭
4. 중복/구버전 후보 탐지
5. 누락/확인필요 항목 생성
6. 표준 제출 폴더 생성
7. 관련 파일 복사/분류
8. INDEX 생성

### Output

```text
준공 준비도
확보 N건
누락 N건
확인 필요 N건
중복/구버전 N건

+ 번호별 준공폴더
+ 문서 INDEX
+ 누락목록
+ 제출용 package
```

첫 프로토타입의 가장 강한 시각적 장면이다.

## 9. 대표 workflow B: 품질관리서 Agent

### 9.1 목적

품질관리서의 작성부터 관계자 확인/날인, 이메일 왕복, 최종본 정리까지 하나의 업무로 관리한다.

### 9.2 Input

- 현장 마스터 정보
- 자재 정보
- 납품확인서
- 시험성적서
- 품질인정/인증 관련자료
- 기존 품질관리서 양식
- 관계자 이메일

### 9.3 Process

```text
관련 증빙 수집
→ 제품/규격/회사정보 추출
→ 품질관리서 작성값 구성
→ HWP 법정서식 작성
→ 제조/유통/시공 등 현재 확인상태 판별
→ 다음 관계자 요청메일 작성
→ 사용자 확인 후 발송
→ 회신 첨부 탐지
→ 이전본과 관계 판단
→ 최신본 후보 등록
→ 다음 단계 진행
→ 최종본 확정
→ 관련 증빙과 함께 제출세트 편입
```

### 9.4 상태 UI 예시

```text
외벽 단열재 품질관리서

제조업자   완료
유통업자   완료
시공자     완료
감리자     회신 대기
건축주     대기

최근 요청: 2026-09-04
최신본: Rev.4
다음 행동: 감리자 회신 확인
```

### 9.5 Prototype boundary

프로토타입에서 HWP 완전자동화가 일정상 무거우면 다음 중 하나로 축소할 수 있다.

- HWP 템플릿 1종만 자동작성
- 생성값 미리보기 후 HWP 수동 반영
- PDF/HTML preview로 작성 결과를 시연

그러나 제품 로드맵에서는 HWP 작성 자동화를 제거하지 않는다.

## 10. 대표 workflow C: 이메일 Agent

### 초기 버전

- 사용자가 현장/누락 항목을 선택
- AIARC가 기존 관계자 정보를 이용해 수신자 추천
- 제목/본문 생성
- 관련 파일 자동 추천
- 사용자가 최종 확인
- 메일 draft 또는 전송

### 확장 버전

```text
요청메일 발송
→ reply/thread 감지
→ 첨부파일 다운로드
→ 현장/문서 자동귀속
→ 내용/날인/버전 확인
→ workflow 상태 변경 제안
→ 다음 관계자 요청 생성
```

메일은 별도 커뮤니케이션 기능이 아니라 **문서 workflow를 움직이는 transport layer**로 취급한다.

## 11. 프로토타입 범위

### MUST

- Windows desktop 중심 UX
- 실제 현장 폴더 선택
- 파일 목록/메타데이터 수집
- 지원 가능한 문서 내용 추출
- 문서 종류 자동분류
- 준공 체크리스트 매칭
- 확보/누락/확인필요 상태
- 준공 폴더 자동 생성
- 파일 자동 분류/복사
- 누락자료 요청메일 생성
- 품질관리서 workflow 화면
- 최소 1개의 문서생성 시연

### SHOULD

- Gmail 또는 Outlook 중 하나 실제 연동
- 회신 첨부를 현장에 자동 편입
- 중복/구버전 탐지
- HWP 템플릿 1종 자동작성
- 현장 마스터 데이터 자동 추출

### MUST NOT block prototype

- 모든 HWP 서식 지원
- 모든 메일 서비스 지원
- 완전 자율 메일발송
- 완전 자동 법적/기술 판정

## 13. 기술 방향

프로토타입 단계에서의 예시 구성이다. 구현 전 실제 기술선택은 재검증한다.

```text
Desktop UI
  ↓
Local File Indexer
  ↓
Document Parsers / OCR
  ↓
AI Extraction & Classification
  ↓
Local Project DB
  ↓
Workflow Engine
  ├─ Folder actions
  ├─ Document generation
  └─ Email actions
```

### Local storage

- 원본파일은 원래 폴더를 유지하는 것을 기본으로 한다.
- AIARC는 인덱스/메타데이터/관계정보를 별도로 관리한다.
- 자동정리는 기본적으로 `copy/preview` 방식부터 시작해 원본 손상 위험을 낮춘다.

### HWP

상용화 전 다음을 별도 검증한다.

- 한컴 HWP Automation/SDK 사용조건
- 상업적 배포 라이선스
- HWP/HWPX 처리 전략
- 한컴오피스 설치 의존성

### Email

초기에는 Gmail API 또는 Microsoft Graph 중 개발이 빠른 하나부터 붙이고, 이후 둘 다 지원한다.

## 14. AI 판단의 신뢰도 설계

모든 자동화를 같은 위험도로 취급하지 않는다.

### Low risk

- 파일 복사
- 폴더 생성
- 파일명 추천
- 문서 종류 후보
- 이메일 초안

기본 자동화 가능.

### Medium risk

- 최신본 판별
- 문서끼리 일치 여부 판단
- 누락자료 판단
- 특정 workflow 단계 완료 판정

근거와 confidence를 보여주고 사용자 확인 가능.

### High risk

- 법적 적합성 최종판정
- 전문기술 판단
- 날인/서명 대행
- 금액/수량 책임결정

자동 확정 금지.

## 15. 보안과 개인정보

건설 문서에는 계약, 도면, 연락처, 견적, 자재정보 등 민감한 자료가 포함될 수 있다.

제품 원칙:

- 최소한의 파일만 AI 추론 대상으로 전송
- 전송 여부와 범위를 사용자에게 명확히 표시
- 가능한 경우 텍스트만 추출하여 처리
- API key/credential은 OS 수준의 안전한 저장소 사용
- 삭제/전송/메일 발송 같은 action은 로그를 남김
- 초기에는 자동발송보다 사용자 확인을 기본값으로 둠

## 16. 성공 기준

첫 프로토타입의 목적은 완성도보다 **업무 대체 가능성 증명**이다.

### Product proof

- 실제 현장 자료에서 문서를 의미있게 분류할 수 있는가
- 준공 요구항목과 자료를 연결할 수 있는가
- 누락자료를 실무자가 납득할 수준으로 보여주는가
- 자동 정리 결과가 사람이 다시 처음부터 정리할 필요가 없는가
- 품질관리서 workflow가 실제 업무 순서를 자연스럽게 표현하는가

### User proof

초기 실무자 인터뷰/데모에서 다음 반응을 확인한다.

- `이 폴더를 실제 현장에 써보고 싶다`
- `이 작업에 실제로 시간이 많이 들어간다`
- `메일과 HWP까지 연결되면 돈을 낼 의향이 있다`
- 어떤 workflow를 다음으로 자동화해야 하는지 구체적 요구가 나온다

### Business proof

- 단순 파일정리 도구가 아니라 공무업무 시간 절감 가치로 인식되는가
- 한 현장 도입이 다른 현장/본사 사용자로 확장될 수 있는가
- 반복적으로 발생하는 자재/준공 workflow에 재사용되는가

## 17. 비목표

AIARC의 초기 목표가 아닌 것:

- 종합 건설 ERP 대체
- BIM 저작도구 대체
- 설계 자동화 전체
- 공사비 적산 엔진 전체
- 법률/감리 책임 대행
- 현장 시공 의사결정 자동화
- 범용 기업 문서관리시스템

AIARC의 시작점은 **건설 공무의 문서 workflow**다.

## 18. 장기 제품 정의

최종적으로 AIARC는 `문서를 어디에 저장했는지`를 알려주는 프로그램을 넘어서야 한다.

```text
메일 수신
→ 문서 이해
→ 현장/자재/공종 연결
→ 필요한 서류 판단
→ 작성
→ 요청
→ 회신 추적
→ 상태 갱신
→ 관련 서류 생성
→ 제출 package 완성
```

장기 North Star:

> **건설 공무 담당자가 파일과 메일을 직접 추적하는 시간을 줄이고, AIARC가 현장의 문서업무 상태를 항상 최신으로 유지하며 다음 필요한 행동을 실행하는 것.**
