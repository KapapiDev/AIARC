# AIARC 제품설계서

Updated: 2026-09-04

## 0. 문서 목적

이 문서는 AIARC의 제품정의, 대상 사용자, 핵심 업무 흐름, 기술 구조, 안전 경계와 프로토타입 범위를 정본으로 기록합니다.

AIARC의 방향은 두 문장으로 요약할 수 있습니다.

> **HWP와 국내 법정서식처럼 복잡하고 특수한 한국의 업무환경부터 깊게 해결한다.**

> **사용자를 새 시스템으로 옮기는 대신, 이미 쓰고 있는 Windows 폴더·이메일·HWP 위에서 문서 업무를 실행한다.**

---

## 1. 제품 정의

**AIARC는 건설회사가 이미 사용하는 이메일, Windows 현장 폴더, HWP 중심의 문서환경 위에서 건설 서류를 이해하고 정리하고 작성하고 추적하여 최종 제출까지 이어주는 local-first 건설 공무 AI 앱입니다.**

한 줄 제품 약속:

> **받은 서류는 정리하고, 작성할 서류는 준비하고, 빠진 자료는 요청하고, 회신과 최신본을 추적해 최종 제출 세트까지 이어줍니다.**

AIARC는 다음을 목표로 하지 않습니다.

- 종합 건설 ERP 전체 대체
- 범용 챗봇
- 단순 PDF OCR·요약기
- 파일명만 바꾸는 정리도구
- 법률·감리·기술 책임을 대신하는 자동판정 시스템

AIARC의 출발점은 **건설 공무의 문서 업무 흐름**입니다.

---

## 2. 해결하려는 문제

### 2.1 문서는 파일이 아니라 업무 상태다

하나의 자재나 공종을 기준으로 여러 문서가 서로 연결됩니다.

```text
Material / Work item
├─ 자재공급원 승인자료
├─ 품질관리서
├─ 납품확인서
├─ 시험성적서
├─ 품질인정·인증자료
├─ 카탈로그·사양서
├─ 반입·시공 사진
├─ 검측·확인자료
└─ 준공·사용승인 제출자료
```

이 자료들은 이메일, 다운로드 폴더, 현장 공유폴더, 개인 PC 등에 흩어지고 같은 문서가 여러 번 왕복합니다.

사람이 실제로 하는 일은 다음과 같습니다.

```text
현장 판단
→ 자재·공종 연결
→ 최신본 확인
→ 관련 증빙 대조
→ 누락 파악
→ 서식 작성
→ 관계자 요청
→ 회신 확인
→ 버전 교체
→ 다음 단계 전달
→ 최종 제출체계 편입
```

문서의 `존재 여부`만 관리해서는 충분하지 않습니다. 문서가 **어떤 현장과 연결되어 있는지, 어느 단계에 있는지, 무엇이 빠졌는지, 다음 행동이 무엇인지**까지 알아야 합니다.

### 2.2 국내 작성환경은 HWP 중심이다

한국 건축·건설 현장의 법정서식과 기관·감리·회사 업무양식에는 HWP가 깊게 들어가 있습니다.

따라서 AIARC의 상용 방향은 단순한 PDF 이해를 넘어 **HWP 작성환경까지 연결되는 Windows 업무 에이전트**입니다.

다만 HWP 완전 자동화는 프로토타입의 선행조건으로 두지 않습니다. 초기에는 일정과 검증 목적에 따라 다음 수준 중 하나를 선택합니다.

1. 실제 HWP 자동작성 1종
2. 제한된 템플릿 자동채움
3. 생성값 미리보기 후 수동 반영

## 3. 초기 대표 법정 업무: 품질관리서

「건축법 시행령」 제62조는 대상 건축자재의 품질관리서에 대해 단계적인 전달·확인 구조를 규정하고 있습니다.

```text
제조업자
→ 유통업자
→ 공사시공자
→ 공사감리자
→ 건축주
→ 사용승인 신청 시 허가권자
```

법령상 핵심 구조는 다음과 같습니다.

- 제조업자는 품질관리서를 유통업자에게 제출합니다.
- 유통업자는 품질관리서와 자재의 일치 여부 등을 확인하고 시공자에게 전달합니다.
- 시공자는 일치 여부를 확인하고 해당 건축물에 사용된 품질관리서 전체를 감리자에게 제출합니다.
- 감리자는 감리완료보고서에 첨부해 건축주에게 제출합니다.
- 건축주는 사용승인 신청 시 허가권자에게 제출합니다.

법령 참고: https://www.law.go.kr/LSW/lsLinkCommonInfo.do?lsJoLnkSeq=1025183813

실무에서는 관련 서식과 증빙이 이메일로 오가며 수정본, 확인본, 날인본이 누적될 수 있습니다. AIARC는 이때 다음 상태를 관리하는 것을 목표로 합니다.

```text
작성 필요
→ 증빙 연결
→ 요청 전
→ 요청 발송
→ 회신 대기
→ 관계자 확인 완료
→ 다음 관계자 전달 필요
→ 최종본
→ 제출자료 편입
```

AIARC는 실제 날인·서명이나 법적 최종판단을 대신하지 않습니다.

### 초기 사용자

- 중소·중견 건설사의 현장 공무 담당자

- 전문건설업체 서류 담당자

### 이후 확장 사용자

- 감리단
- 건축사사무소·설계사
- CM·PM
- 시행사·건축주 측 공사관리 조직
- 자재 제조·유통업체

외부 관계자가 모두 AIARC 계정을 가져야 하는 구조는 피합니다. **상대방은 기존 이메일만 사용해도 업무 흐름에 참여할 수 있어야 합니다.**

## 5. 제품 원칙

### P1. Existing workflow first

Outlook·Gmail, Windows 폴더, HWP를 최대한 유지합니다. 사용자가 AIARC 때문에 같은 자료를 다시 업로드·분류·입력하게 만들지 않습니다.

### P2. Local-first

원본 파일과 현장 인덱스는 가능한 한 사용자 PC 또는 회사 저장소 중심으로 관리합니다.

`local-first`는 `완전 오프라인`과 같은 뜻이 아닙니다. 필요한 AI 추론만 외부 모델을 사용할 수 있으며, 향후 고객 보안 요구에 따라 private cloud, on-premise, local model을 검토합니다.

### P3. HWP-aware

HWP를 부가 호환기능이 아니라 국내 제품의 핵심 업무환경으로 취급합니다.

### P4. Workflow, not chatbot

`무엇이 누락됐는가`에서 끝나지 않고 요청메일, 회신, 상태 갱신, 최종 편입까지 이어지는 **다음 행동**을 제품의 일부로 봅니다.

### P5. Evidence before automation

AI가 추출하거나 판단한 값은 가능한 한 원문 파일·메일·페이지 근거와 연결합니다. 확신도가 낮으면 자동 확정하지 않고 `확인 필요` 상태로 둡니다.

### P6. Human authority remains

다음은 자동 확정하지 않습니다.

- 실제 날인·서명
- 법적 적합성 최종판단
- 기술 책임자의 최종확인
- 설계변경 타당성 최종판단
- 기성률·공사수량 책임확정

### P7. Narrow workflow first

하나의 업무 흐름을 입력부터 결과까지 끝낸 뒤 인접 업무로 확장합니다.

### P8. Korea-depth before global breadth

글로벌 범용성을 위해 국내 기능을 얕게 만들지 않습니다. 국내에서 실제 업무 깊이를 확보하는 것이 먼저입니다.

## 6. 다섯 가지 핵심 능력

### UNDERSTAND

- 현장 판별
- 문서 종류 판별
- 공종·자재 판별
- 관계자 추출
- 제품명·규격·날짜·번호 추출
- 관련 문서 연결

### ORGANIZE

- 현장·자재·공종별 자동귀속
- 준공항목 매칭
- 표준 파일명 추천
- 중복 탐지
- 최신본·구버전 후보 판별
- 제출 문서묶음 구성

### CREATE

- 현장 마스터 데이터 재사용
- 기존 법정·회사 양식 기반 작성
- HWP 템플릿 자동화
- INDEX·총괄표 생성
- 품질관리서 등 반복서식 작성 보조

### ACT

- 누락자료 요청메일 초안 생성
- 수신자·첨부자료 추천
- 사용자 승인 후 발송
- 향후 후속 요청·재요청·다음 단계 실행

### TRACK

- 문서 생명주기 상태
- 관계자별 확인상태
- 요청·회신상태
- 버전관계
- 제출 준비상태

## 7. 핵심 데이터 모델: Project Document Graph

AIARC의 장기 자산은 파일목록이 아니라 **문서 관계 그래프**입니다.

```text
Project
├─ Parties
├─ Contracts
├─ Materials
├─ Work items
├─ Documents
├─ Email threads
├─ Revisions
├─ Approvals
└─ Workflow instances
```

### Document

```text
문서 종류
원본 파일 경로
원본 메일·thread
현장
자재·공종
발신자·작성자
버전
상태
추출 데이터
관련 문서
근거
```

### Workflow Instance

```text
workflow type
현재 단계
담당·관계자
필요 문서
완료 문서
누락 문서
최근 요청일
최근 회신일
다음 행동
최종 결과물
```

이 구조가 쌓이면 다음 질문에 답할 수 있습니다.

- 이 자재의 최신 승인본은 무엇인가
- 감리에게 보냈지만 답이 없는 문서는 무엇인가
- 준공에 필요한데 아직 확보하지 못한 자료는 무엇인가
- 시험성적서와 납품확인서의 규격이 다른 후보는 무엇인가
- 설계변경 이후 영향을 받을 문서는 무엇인가

## 8. 대표 업무 A: 준공서류 자동정리

### 입력

- 실제 또는 익명화된 현장 폴더
- 현장별 준공 요구목록 또는 기준 폴더구조
- 이메일에서 확보한 첨부자료

### 처리

```text
파일 스캔
→ 문서 분류
→ 준공항목 매칭
→ 중복·구버전 후보 탐지
→ 확보·누락·확인 필요 상태 생성
→ 번호별 제출 폴더 생성
→ 파일 복사·분류
→ INDEX 생성
```

### 결과

```text
준공 준비도
확보 N건
누락 N건
확인 필요 N건
중복·구버전 후보 N건

+ 제출 폴더
+ INDEX
+ 누락목록
+ 최종 package 후보
```

## 9. 대표 업무 B: 품질관리서 Agent

```text
관련 증빙 수집
→ 제품·규격·회사정보 추출
→ 품질관리서 작성값 구성
→ HWP·서식 작성
→ 현재 관계자 확인상태 파악
→ 다음 관계자 요청메일 작성
→ 회신 감지
→ 첨부파일 귀속
→ 이전본과 버전관계 판단
→ 다음 단계 진행
→ 최종본 확정
→ 관련 증빙과 제출세트 편입
```

상태 UI 예시:

```text
외벽 단열재 품질관리서

제조업자   완료
유통업자   완료
시공자     완료
감리자     회신 대기
건축주     대기

최근 요청: 2026-09-04
최신본: Rev.4
다음 행동: 감리자 회신 확인
```

## 10. 대표 업무 C: 이메일 Agent

초기:

```text
누락항목 선택
→ 수신자 추천
→ 제목·본문 생성
→ 첨부 추천
→ 사용자 확인
→ draft 또는 전송
```

확장:

```text
요청메일 발송
→ reply·thread 감지
→ 첨부 다운로드
→ 현장·자재·문서 자동귀속
→ 내용·버전 확인
→ workflow 상태 변경 제안
→ 다음 관계자 요청
```

이메일은 단순 커뮤니케이션 기능이 아니라 **업무 흐름을 이동시키는 전달 계층**입니다.

## 11. 모두의 창업 프로토타입 범위

### 반드시 보여줄 것

- Windows desktop 중심 UX
- 현장 폴더 선택
- 파일 목록·메타데이터 수집
- 지원 가능한 문서내용 추출
- 문서 종류 분류
- 준공 체크리스트 매칭
- `확보 / 누락 / 확인 필요 / 중복` 표시
- 번호별 준공 폴더 생성
- 파일 분류·복사 시연
- 누락자료 요청메일 생성
- 품질관리서 업무 흐름 UI
- 최소 1개의 문서생성 결과 시연

### 가능하면 포함할 것

- Gmail 또는 Outlook draft 연동
- 회신 첨부 자동편입
- 중복·구버전 탐지
- HWP 템플릿 1종 자동작성
- 현장 마스터 자동추출

### 프로토타입을 막아서는 안 되는 항목

- 모든 HWP 서식 지원
- 모든 메일서비스 연동
- 완전자율 메일발송
- 법적·기술적 완전 자동판정
- 다수 조직 권한체계
- 모든 ERP 연동
- 자체 LLM 개발
- 온프레미스 AI 완성

## 12. 프로토타입 실행 구조

1차 프로토타입은 `제품을 어떻게 보여줄 것인가`와 `최종 기술구조`를 분리합니다.

```text
Desktop UI
   ↓
Agent Interface
   ├─ DemoEngine      ← 1차 고정·익명화 샘플 데이터
   └─ RealAIEngine    ← 이후 parser / model / email / HWP
```

### DemoEngine 원칙

- 구현되지 않은 기능을 실제 AI 기능처럼 보이게 하지 않습니다.
- 화면에 `Prototype Demo` 또는 `Demo Mode`를 명확히 표시합니다.
- 시뮬레이션 기능과 실제 파일 동작을 구분합니다.
- 가능하면 폴더 생성, 샘플파일 복사 등 일부 동작은 실제로 수행합니다.

이 구조를 사용하면 1차에서는 제품가설을 빠르게 시연하면서도 이후 RealAIEngine으로 교체할 수 있는 인터페이스를 유지할 수 있습니다.

---

## 13. LLM·API 비용과 보안 원칙

공개 배포되는 desktop binary 안에 **AIARC가 소유한 LLM API secret을 포함하지 않습니다.**

프로토타입과 초기 제품은 다음 순서로 검토합니다.

1. **DemoEngine**: LLM 없이 고정·익명화 샘플로 시연
2. 필요 시 **BYOK**: 사용자가 본인 provider key를 로컬에 등록
3. 필요 시 **local model**: Ollama 등 로컬 추론 옵션 검토
4. 상용화 후 **AIARC-managed inference**: 서버측 gateway, 인증, 사용량 제한, 과금체계 아래 제공

API key는 로그·저장소·실행파일에 평문으로 포함하지 않습니다. 실제 제품에서는 OS 수준의 안전한 저장소 사용을 우선합니다.

## 14. 위험도에 따른 자동화

### 낮은 위험

- 파일 복사
- 폴더 생성
- 파일명 추천
- 문서 종류 후보 제시
- 이메일 초안 작성

자동화 강도를 높일 수 있습니다.

### 중간 위험

- 최신본 판별
- 문서 간 정보 일치 여부 판단
- 누락자료 판단
- 업무 단계 완료 후보 판정

근거와 신뢰도를 함께 보여주고 사용자가 수정할 수 있어야 합니다.

### 높은 위험

- 법적 적합성 최종판정
- 전문기술 판단
- 날인·서명 대행
- 금액·수량 책임결정

자동 확정하지 않습니다.

## 15. 보안·데이터 원칙

건설 문서에는 도면, 계약, 견적, 연락처, 자재정보 등 민감한 자료가 포함될 수 있습니다.

- 원본은 기존 위치 보존을 기본으로 합니다.
- 자동정리는 우선 `copy / preview` 방식으로 시작합니다.
- AI 추론에 보내는 데이터는 최소화합니다.
- 외부 전송범위를 사용자에게 명확히 표시합니다.
- 가능하면 필요한 텍스트만 추출해 처리합니다.
- 삭제·전송·메일 동작에는 로그를 남깁니다.
- 실제 현장자료는 저장소에 포함하지 않습니다.
- 공개 데모는 익명화된 데이터셋을 사용합니다.

## 16. 성공 기준

### 제품 검증

- 실제 현장자료에서 문서를 의미 있게 분류하는가
- 준공 요구항목과 보유자료를 연결하는가
- 누락·확인 필요 상태가 실무자가 납득 가능한가
- 자동정리 결과를 사람이 처음부터 다시 만들 필요가 없는가
- 품질관리서 업무 흐름이 실제 업무와 자연스럽게 맞는가

### 사용자 검증

- 현장 실무자가 실제 자기 폴더에 써보고 싶다고 말하는가
- 반복 사용이 발생하는가
- 어떤 자동화가 가장 가치 있는지 구체적 요구가 나오는가
- HWP·메일 연동의 지불가치를 확인할 수 있는가

### 사업 검증

- 단순 파일정리보다 `공무업무 시간 절감` 가치로 인식되는가
- 한 현장에서 다른 현장·본사로 확장되는가
- 반복 업무에서 계속 사용되는가

## 17. 장기 제품 정의

AIARC의 장기 North Star는 다음 문서 생명주기를 하나의 공통 엔진으로 다루는 것입니다.

```text
수집
→ 이해
→ 관계 연결
→ 생성
→ 검토
→ 전달
→ 회신 추적
→ 버전 관리
→ 제출
```

국내에서는 HWP, 국내 법정서식, 국내 감리·시공 업무를 깊게 해결합니다.

장기적으로는 설계·감리·시공·발주·자재업체 등 건축 프로젝트 참여자의 문서 흐름 전체를 연결하는 **Architecture Document AX Platform**으로 확장합니다.

글로벌은 현재 제품 요구사항이 아니라 장기 옵션입니다. 국내에서 충분한 업무 깊이와 Document Graph 자산을 만든 뒤에만 국가별 문서·법규·업무체계에 맞춰 다시 검증합니다.
