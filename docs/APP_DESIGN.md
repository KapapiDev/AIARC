# AIARC 데스크톱 앱 설계서

Updated: 2026-09-08
Status: Current design baseline

## 0. 문서 목적

이 문서는 AIARC 데스크톱 앱의 기본 UI 구조와 핵심 UX를 정본으로 기록한다.

AIARC의 화면은 범용 LLM 채팅앱이 아니라 **건설 문서 업무를 자동으로 처리하는 데스크톱 작업공간**이어야 한다.

핵심 경험은 다음 한 줄로 정의한다.

> **사용자는 파일·폴더·압축파일을 던지고, AIARC가 알아서 분석·정리한 뒤, 사용자는 필요한 순간에만 딸깍한다.**

사람에게 문서 분류 업무를 다시 시키지 않는다. 대화와 뷰어는 자동화를 대신하는 절차가 아니라, AIARC를 지시하고 결과 근거를 확인하기 위한 인터페이스다.

---

## 1. 제품 형태

AIARC는 **Windows 중심 데스크톱 앱**을 기본 전제로 한다.

주요 입력원:

- Windows 파일 및 폴더
- ZIP 등 압축파일
- HWP / HWPX
- PDF
- XLSX / DOCX 등 업무문서
- 이미지·스캔본
- 이메일 및 이메일 첨부파일

제품은 웹 업로드 중심 SaaS가 아니라 사용자의 기존 Windows 업무환경 위에서 작동하는 local-first 앱을 지향한다.

## 2. UX 최상위 원칙

### UX1. Automation first, conversation second

정상적인 문서는 AIARC가 알아서 처리한다.

좋지 않은 흐름:

```text
파일 드롭
→ AIARC: 이 문서는 시험성적서입니다. 어디에 넣을까요?
→ 사용자: 자재 > 단열재에 넣어줘
→ AIARC: 정리할까요?
→ 사용자: 네
```

지향 흐름:

```text
파일·폴더 드롭
→ AIARC 자동 분석
→ 현장·공종·자재·문서종류 자동 판별
→ 중복·버전·누락·확인 필요 탐지
→ 정리안 생성
→ [전체 정리]
→ 완료
```

사용자는 문서가 무엇인지 직접 확인하지 않아도 되어야 한다.

### UX2. 사람은 작업자가 아니라 승인자다

AX의 목표는 사람이 모든 중간 판단을 수행하는 것이 아니다.

사용자의 기본 행동은 다음으로 제한한다.

1. 자료를 넣는다.
2. AIARC가 만든 결과 또는 예외를 확인한다.
3. 필요한 경우 버튼 한 번으로 반영한다.

### UX3. 정상건은 조용히, 예외만 사람에게

AIARC가 충분한 확신을 가진 문서는 자동 분류한다.

예:

```text
243개 문서 분석 완료
231개 자동 정리 가능
7개 중복 후보
5개 확인 필요

[전체 정리]
```

애매한 5개 때문에 243개 전체를 사용자가 확인하게 만들지 않는다.

### UX4. Evidence on demand

사용자가 AI의 판단 근거를 확인하고 싶을 때만 뷰어를 사용한다.

예:

```text
시험성적서 제품명: ABC-120
자재승인원 제품명: ABC-100
→ 불일치 후보
```

사용자가 해당 경고를 클릭하면 뷰어가 관련 페이지와 위치를 열고 근거를 보여준다.

### UX5. One UI, one login, site-scoped work

`본사 직원 UI`와 `현장 직원 UI`를 별도로 만들지 않는다.

같은 사람이 본사와 현장을 오갈 수 있으며 같은 로그인으로 여러 현장을 관리할 수도 있다.

따라서 사람의 역할을 기준으로 모드를 나누지 않는다.

```text
사람을 나누지 않는다.
UI를 나누지 않는다.
현재 작업할 현장만 선택한다.
```

## 3. 기본 앱 셸

현재 기준 기본 화면은 다음과 같다.

```text
┌──────────────────────────────────────────────────────────────┐
│ AIARC                                             설정  ⌄   │
├───────────────┬──────────────────────────────────────────────┤
│               │                                              │
│ 현장          │                  문서 뷰어                    │
│ ▾ OOO 근린생활시설 │                                          │
│               │          현재 선택한 문서 미리보기           │
│ 문서          │                                              │
│ ├ 자재        │                                              │
│ ├ 품질        │                                              │
│ ├ 감리        │                                              │
│ ├ 공사        │                                              │
│ └ 준공        │                                              │
│               ├──────────────────────────────────────────────┤
│ 확인 필요   3 │ AIARC                                       │
│ 누락        5 │                                              │
│               │ 243개 문서를 분석했습니다.                  │
│               │ 231개 자동 정리 가능                        │
│               │ 7개 중복 후보 · 5개 확인 필요              │
│               │                                              │
│               │        [ 전체 정리 ]   [ 검토하기 ]         │
│               │                                              │
│               │ ┌──────────────────────────────────────────┐ │
│               │ │ AIARC에게 지시하거나 파일을 드롭하세요 │ │
│               │ └──────────────────────────────────────────┘ │
│               │                                              │
├───────────────┤                                              │
│ 신규 메일 2건│                                              │
│ [ 가져오기 ] │                                              │
└───────────────┴──────────────────────────────────────────────┘
```

화면은 크게 두 영역이다.

- **좌측:** 현장 + 문서 구조 + 예외 상태 + 외부 문서 유입
- **중앙:** 큰 문서 뷰어 + 작은 AI 대화/명령 영역

우측에 별도의 상시 패널을 추가하지 않는 것을 기본으로 한다. 필요한 상태와 행동은 좌측 트리와 중앙 AI 영역 안에 통합한다.

## 4. 좌측 사이드바

### 4.1 현장 선택

좌측 상단의 가장 중요한 컨텍스트는 `현재 현장`이다.

```text
현장
▾ OOO 근린생활시설
```

현장 선택기를 누르면 사용 가능한 현장 목록을 보여준다.

```text
현장 선택

OOO 근린생활시설
OOO 공동주택
OOO 물류센터

+ 새 현장
```

한 현장만 관리하는 사용자는 선택기를 거의 건드릴 필요가 없다.

여러 현장을 관리하는 사용자도 동일한 UI에서 현장만 바꾸면 된다.

`본사 모드 / 현장 모드` 같은 별도 토글은 두지 않는다.

### 4.2 문서 트리

현재 현장의 문서 구조를 표시한다.

초기 기본안:

```text
문서
├ 자재
├ 품질
├ 감리
├ 공사
└ 준공
```

이 분류는 프로토타입 검증 과정에서 실제 현장 문서구조에 맞게 조정할 수 있다.

장기적으로는 단순한 실제 폴더 복제가 아니라 AIARC의 Project Document Graph와 연결된 업무 구조를 표현해야 한다.

예:

```text
자재
└ 단열재
   ├ 자재승인원
   ├ 시험성적서
   ├ 납품확인서
   └ 인증자료
```

### 4.3 AI 예외 상태

문서 트리와 별도로 사용자가 바로 행동해야 할 항목을 노출한다.

```text
확인 필요   3
누락        5
```

향후 필요 시 다음 상태를 추가할 수 있다.

- 기입 누락
- 불일치
- 중복 후보
- 미분류
- 회신 대기

단, 사이드바를 상태 메뉴로 과밀하게 만들지 않는다. 실제 사용빈도가 검증된 항목부터 추가한다.

### 4.4 신규 메일 / 가져오기

좌측 하단은 새로운 문서가 들어오는 `유입 지점`이다.

```text
신규 메일 2건
[ 가져오기 ]
```

메일 가져오기 흐름:

```text
신규 이메일 감지
→ 첨부파일 확인
→ 현재 현장 또는 다른 현장 판별
→ 문서 종류·자재·공종 판별
→ 중복·최신본 후보 확인
→ 정리안 생성
→ 사용자 승인 또는 자동귀속
```

사용자가 이메일 첨부파일을 PC에 따로 저장한 뒤 AIARC에 다시 업로드하도록 만들지 않는 것이 목표다.

향후 이메일 외에도 공유폴더, 스캔함 등 다른 유입원을 같은 위치로 확장할 수 있지만 초기 UI에서는 이메일부터 단순하게 시작한다.

## 5. 중앙 문서 뷰어

### 5.1 뷰어가 화면의 주인공

중앙 작업영역의 대부분은 문서 뷰어가 차지한다.

권장 초기 비율:

- 사이드바: 전체 폭의 약 18~22%
- 중앙 작업영역: 약 78~82%
- 중앙 안에서 AI 대화/명령 영역: 높이 약 20~25%
- 나머지: 문서 뷰어

정확한 수치는 구현 후 시각 검증으로 조정한다.

### 5.2 뷰어의 역할

뷰어는 사용자가 모든 문서를 직접 검토하도록 강요하기 위한 화면이 아니다.

주요 역할:

- 현재 선택한 문서 미리보기
- AI 판단 근거 확인
- 누락·불일치 후보 위치 표시
- 특정 필드 및 페이지 하이라이트
- 관련 문서 간 비교

즉 **기본 업무절차가 아니라 증거 확인 장치**다.

### 5.3 문서 포맷

목표 지원 포맷:

- PDF
- HWP
- HWPX
- 이미지·스캔본
- XLSX / DOCX 등 인접 업무문서

원본 파일은 보존한다.

HWP/HWPX는 AIARC가 직접 완전한 편집기를 만드는 것을 선행조건으로 하지 않는다. 파싱·렌더링·미리보기 계층을 분리하고 필요 시 기존 엔진이나 변환 방식을 활용한다.

## 6. 중앙 AI 대화 / 명령 영역

### 6.1 Chatbot이 아니라 Command Interface

대화영역은 ChatGPT처럼 화면의 중심을 차지하지 않는다.

기본 상태에서는 작고 얇게 유지하며 사용자가 긴 대화를 할 때만 확장할 수 있다.

역할:

- AIARC 작업상태 설명
- 정리 결과 요약
- 예외사항 알림
- 사용자 승인 요청
- 자연어 추가지시
- 선택 문서에 대한 질문

예:

```text
AIARC
243개 문서를 분석했습니다.
231개 자동 정리 가능
7개 중복 후보 · 5개 확인 필요

[전체 정리] [검토하기]

AIARC에게 지시하거나 파일을 드롭하세요
```

### 6.2 사용자가 대화하지 않아도 업무가 끝나야 한다

정상 흐름에서 사용자의 텍스트 입력은 필수가 아니다.

사용자는 필요할 때만 다음처럼 지시한다.

```text
단열재 관련 서류만 다시 검토해줘
```

```text
준공 제출 기준으로 다시 정리해줘
```

```text
이 시험성적서가 어떤 승인원과 연결되는지 보여줘
```

대화는 AIARC의 전체 기능을 자연어로 조종하는 인터페이스이며, 분류를 하나씩 가르치는 과정이 아니다.

## 7. Drag & Drop 기본 흐름

AIARC의 대표 UX다.

지원 대상:

- 단일 파일
- 여러 파일
- 폴더
- ZIP 등 압축파일

목표 경험:

```text
사용자가 폴더를 중앙에 드롭
        ↓
AIARC가 자동으로 스캔
        ↓
현장 / 문서 종류 / 자재 / 공종 / 관계 문서 판별
        ↓
중복 / 최신본 / 누락 / 확인 필요 탐지
        ↓
정리 결과 미리 계산
        ↓
[전체 정리]
        ↓
문서 트리 반영
        ↓
완료
```

드롭 직후 사용자가 개별 파일을 하나씩 확인할 필요가 없어야 한다.

### 예시

```text
OOO근린생활시설_준공서류.zip

243개 문서를 분석했습니다.
231개 자동 분류 가능
7개 중복 후보
5개 확인 필요

[전체 정리]
```

사용자가 `전체 정리`를 누르면 좌측 문서트리가 즉시 갱신된다.

## 8. 문서 자동화와 AI 처리 원칙

### 8.1 분류와 검토를 구분한다

`이 문서가 무엇인가`와 `이 문서가 완전하고 올바른가`는 다른 문제다.

분류:

```text
시험성적서인지 판별
→ 현장·자재·업체 연결
→ 적절한 위치에 귀속
```

검토:

```text
필수 문서 존재 여부
필수 기입항목 누락
서명·날인 후보 확인
제품명·규격·업체 등 관계문서 불일치
유효기간·발급일 등 검토
```

### 8.2 문서를 무조건 최상급 LLM에 통째로 넣지 않는다

비용과 속도를 위해 단계적으로 처리한다.

```text
파일 메타데이터 / 파일명 / 경로
→ 텍스트 레이어 / OCR / Layout 분석
→ 문서 유형 후보
→ 문서별 검증 Schema
→ 필요한 필드와 페이지 탐색
→ 규칙·소형 모델 처리
→ 애매한 사례만 강한 모델
→ 그래도 불명확하면 확인 필요
```

문서 전체를 검색 가능하게 만드는 것과 문서 전체를 강한 LLM이 읽는 것은 구분한다.

### 8.3 Document Schema

문서 종류가 판별되면 해당 문서에 필요한 검증 기준을 적용한다.

예:

```text
시험성적서
├ 성적서 번호
├ 시험기관
├ 제품명
├ 제조사
├ 발급일
├ 유효기간 또는 적용기간
├ 시험·인증 항목
└ 관련 자재승인 자료
```

이를 기반으로 문서 중간 페이지의 빈 필드나 관계문서 누락도 탐지할 수 있어야 한다.

### 8.4 Document Graph

문서를 개별 파일로만 보지 않는다.

예:

```text
단열재
├ 자재승인원       ✓
├ 시험성적서       ✓
├ 납품확인서       ✕
├ 인증자료         ✓
└ 감리 확인        △
```

AIARC는 이 관계를 이용해 `파일이 없다`, `값이 다르다`, `최신본이 아니다`, `다음 단계 자료가 없다` 같은 상태를 찾는다.

## 9. 인터랙션 예시

### 시나리오 A: 폴더 자동정리

```text
[사용자]
현장 폴더 드롭

[AIARC]
243개 문서를 분석했습니다.
231개를 현재 현장 문서구조에 자동 정리할 수 있습니다.
7개는 중복 후보이며 5개는 확인이 필요합니다.

[전체 정리]
```

사용자는 `전체 정리` 한 번으로 정상 문서를 처리한다.

### 시나리오 B: 누락 발견

```text
AIARC
단열재 관련 자재승인원과 시험성적서는 확인했습니다.
대응되는 납품확인서를 찾지 못했습니다.

[근거 보기] [요청 준비]
```

`근거 보기`를 누르면 중앙 뷰어가 관련 문서를 연다.

### 시나리오 C: 문서 값 불일치

```text
AIARC
제품명 불일치 후보를 발견했습니다.

자재승인원: ABC-100
시험성적서: ABC-120

[문서 비교]
```

`문서 비교`를 누르면 뷰어가 두 근거 위치를 보여준다.

### 시나리오 D: 이메일 가져오기

```text

[반영하기]
```

## 10. 프로토타입 디자인 범위

모두의 창업용 프로토타입에서는 실제 모든 기능을 구현할 필요는 없지만 **최종 제품의 UX를 왜곡하지 않는다.**

반드시 보여줄 핵심 장면:

1. AIARC 데스크톱 앱 셸
2. 현장 선택
3. 좌측 문서트리
4. 파일·폴더·ZIP Drag & Drop
5. 자동 분석 상태
6. `전체 정리` 한 번으로 문서트리 변화
7. `확인 필요` / `누락` 상태
8. 중앙 큰 문서 뷰어
9. 문제 근거 하이라이트 또는 비교
10. 하단 작은 AI 대화/명령 영역
11. 좌하단 `신규 메일 N건 / 가져오기`

프로토타입의 핵심 메시지:

> **건설 문서를 AI와 대화하며 하나씩 정리하는 앱이 아니다. 파일을 던지면 AIARC가 먼저 일하고, 사람은 필요한 순간에만 확인하고 승인한다.**

## 11. 구현 시 지켜야 할 디자인 금지사항

다음 방향으로 변질시키지 않는다.

- ChatGPT 클론처럼 대화창을 화면 대부분으로 구성
- 문서 하나마다 사용자에게 분류 위치 질문
- `본사 모드 / 현장 모드`로 화면을 둘로 분리
- 역할별 별도 로그인 흐름을 UI 핵심으로 설계
- 지나치게 많은 우측 패널과 대시보드 카드 추가
- 자동화할 수 있는 중간 절차를 사용자 클릭 단계로 노출
- 뷰어를 단순 장식용 PDF 영역으로 사용
- 실제 문서 구조보다 시각 효과를 우선

## 12. 현재 확정 베이스라인

현재 앱 설계의 정본은 다음과 같다.

```text
Desktop-first
+ Local-first
+ One UI
+ Site selector
+ Left document tree
+ Large central viewer
+ Small expandable AI command area
+ Drag & Drop intake
+ Email intake
+ Automatic organization by default
+ Exceptions only when needed
+ Evidence on demand
```

한 문장으로 요약하면:

> **좌측에는 현재 현장의 문서 세계를, 중앙에는 AIARC가 보고 있는 문서와 판단 근거를 두고, 사용자는 자료를 던진 뒤 결과를 승인하는 데스크톱 AX 작업공간.**
